## Дефекты

### FW-05 (`fail`): брандмауэр узла пропускает WinRM с любого адреса

Ожидалось: на узле разрешены ровно заявленные входящие порты — 22 и 3389,
остальное закрыто.

Фактически: включены два штатных правила WinRM, оба без ограничения по адресу:

- «Windows Remote Management (HTTP-In)», порт 5985, профили Domain и Private,
  `RemoteAddress=Any`;
- «Windows Remote Management (HTTPS-In)», порт 5986, профиль Any,
  `RemoteAddress=Any`.

Интерфейс `Ethernet` отнесён к профилю Public, поэтому правило для 5985 сейчас
не действует, а правило для 5986 действует во всех профилях и потому активно.
Служба WinRM запущена с автозапуском и принимает `Negotiate`/`Kerberos`, то есть
аутентификацию по паролю.

Шаги воспроизведения:

```powershell
# на цели
Get-NetFirewallRule -DisplayGroup 'Windows Remote Management' |
    Where-Object Enabled -eq 'True' |
    ForEach-Object {
        '{0} | профиль={1} | порт={2} | RemoteAddress={3}' -f $_.DisplayName, $_.Profile,
            ($_ | Get-NetFirewallPortFilter).LocalPort,
            ($_ | Get-NetFirewallAddressFilter).RemoteAddress
    }
Get-Service WinRM | Select-Object Status, StartType
winrm enumerate winrm/config/listener
```

Или целиком: `scripts\qa\run-check-target.ps1`, пункт FW-05.

Влияние: заявлено, что канал управления — SSH по ключу, а вход по паролю
отключён. WinRM даёт второй административный канал с аутентификацией по паролю.
Сейчас снаружи он недоступен, но исключительно потому, что его закрывает
брандмауэр Google Cloud: на самом узле он разрешён. Защита держится на одном
рубеже, о котором в `environments.md` не сказано, и любое расширение правил VPC
или перенос образа на другую площадку открывает этот путь без каких-либо
изменений на узле.

Проверка внешней недоступности (с машины оркестратора):

```powershell
foreach ($p in 22,135,445,3389,5985,5986,47001) {
    $c = New-Object System.Net.Sockets.TcpClient
    $ar = $c.BeginConnect('35.208.225.47', $p, $null, $null)
    $ok = $ar.AsyncWaitHandle.WaitOne(5000, $false)
    '{0,-6} {1}' -f $p, $(if ($ok) { 'OPEN' } else { 'TIMEOUT/FILTERED' })
    $c.Close()
}
```

Результат: `22 OPEN`, `3389 OPEN`, остальные `TIMEOUT/FILTERED`.

### OS-03 (`warn`): отложенные операции с файлами

`PendingFileRenameOperations` содержит 15 записей: обновление Microsoft Edge и
файлы очереди печати. Жёстких признаков незавершённой установки
(`Component Based Servicing\RebootPending`, `WindowsUpdate\RebootRequired`,
переименование машины) нет, поэтому это не блокирующий дефект: система
работоспособна, часть файлов будет заменена при следующей загрузке. Отмечено
потому, что первую же перезагрузку узла нужно планировать с учётом этого — она
будет не «чистой».

### FW-01, FW-02 (`warn`): 22 и 3389 приняты с любого адреса

Соответствует решению владельца, зафиксированному в `environments.md`, и потому
не дефект. Два замечания по устойчивости:

- для 22 есть два правила, и одно из них («OpenSSH SSH Server (sshd)», профиль
  Private) при текущем профиле Public не действует. Доступ по SSH держится на
  единственном действующем правиле «OpenSSH Server (sshd) 22». Если его снять,
  например при неаккуратном применении `-MeshOnly`, управление будет потеряно, а
  `GCEAgent` отключён и сброс пароля из консоли GCP недоступен;
- обратный порядок в `setup-windows-target.ps1` учтён верно: `-MeshOnly` сначала
  проверяет доступность концентратора меша.

### WRM-01 (`warn`): WinRM запущен и не заявлен

Причина `fail` в FW-05 — правила брандмауэра, но сама служба тоже вне описания
окружения. Если WinRM не нужен платформе, правильное состояние — служба
отключена и правила выключены; если нужен, он должен быть описан в
`environments.md` вместе с моделью его аутентификации.

### OS-04 (`blocked`): регресс после перезагрузки

Бриф требует проверить, что после перезагрузки узел поднимается без ручных
действий. Проверка не выполнена: перезагрузка меняет состояние единственного
тестового узла и при неверной конфигурации автозапуска отрезает доступ
безвозвратно, поскольку `GCEAgent` отключён. Нужно согласие владельца и окно.

Косвенные свидетельства в пользу того, что регресса не будет: `sshd`
`StartMode=Auto` и запускается от `LocalSystem`; `TermService` в состоянии
`Running` со штатным `StartMode=Manual` (запуск по триггеру входящего
подключения); правило брандмауэра для 22 постоянное, а не временное. Настройки
`DefaultShell`, NLA, `SecurityLayer` и SMBv1 хранятся в реестре и переживают
перезагрузку по определению.

Порядок проверки, когда окно будет: зафиксировать `LastBootUpTime`, выполнить
`Restart-Computer`, дождаться ответа 22 порта, затем прогнать
`run-check-target.ps1` и сравнить результат с этим отчётом. Ключевой признак
дефекта — необходимость любого ручного действия.

## Риски безопасности

Помимо дефектов по поставленной задаче.

1. **Второй канал управления с паролем (WinRM).** Описан выше как FW-05.
   Наиболее серьёзное из найденного: он обесценивает заявление «вход только по
   ключу», а держится только на облачном брандмауэре.

2. **RDP на 3389 доступен из интернета и принимает пароль.** Решение владельца,
   зафиксированное в `environments.md`, машина одноразовая. Смягчающие
   обстоятельства подтверждены фактически: NLA включена, `SecurityLayer=2`,
   порог блокировки 10 попыток, встроенный `Administrator` отключён, а
   `AllowAdministratorLockout=1`, то есть подбор по единственной включённой
   записи `root` приведёт к её блокировке. Тем не менее это постоянный поток
   попыток входа, и для боевого узла путь один — доступ только через меш.

3. **Исходящий трафик с узла не ограничен.** `DefaultOutboundAction` во всех
   профилях `NotConfigured`, то есть разрешено всё. Egress-политика из
   `docs/design/egress.md` описана только для VPS с `ufw`; для Windows-цели
   такого рубежа нет вообще. Когда на цель попадёт агент платформы, вопрос
   «звонит ли оно домой» на этом узле проверить будет нечем.

4. **Единственный ключ и единственный путь восстановления.** В
   `administrators_authorized_keys` один ключ, `GCEAgent` отключён, встроенный
   `Administrator` отключён. Потеря приватного ключа означает потерю машины.
   Права на файл ключей выставлены верно, но резервного пути нет.

5. **Лишние слушатели на узле.** Кроме 22 и 3389 слушают 135, 445, 5985, 5986,
   47001, а также агенты Google Cloud на 20201 и 20202. Снаружи они закрыты
   облачным брандмауэром, но на самом узле — нет. Это та же однорубежная
   защита, что и в FW-05, только с меньшим весом: правил, разрешающих 135, 139,
   445 и 47001 с любого адреса, не найдено.

6. **SMB без обязательного подписывания.** `RequireSecuritySignature=False`.
   В сочетании с открытым 445 внутри VPC это допускает подмену в пути. Для
   одноразового тестового узла второстепенно.

7. **`CbtHardeningLevel=Relaxed` у WinRM.** Ослабляет привязку канала при
   аутентификации. Значимо только если WinRM останется включённым.

## Вердикт

Заявленное в `environments.md` и `setup-windows-target.ps1` подтверждено
фактически: sshd запущен и на автозапуске, вход по паролю действительно
отвергается, вход по ключу работает, оболочка sshd — PowerShell, файл ключей
администратора лежит там, где нужно, и с правильными правами, NLA и TLS для RDP
включены, SMBv1 выключен, роли RDS не установлены, режим лицензий `1`.
Расхождений с описанием окружения, кроме перечисленных ниже, нет.

Как тестовый узел для дальнейшей работы сервер пригоден. Блокирующих дефектов
для продолжения тестирования нет.

Что должно быть закрыто до того, как эта конфигурация станет образцом для
боевого узла:

- FW-05 — выключить WinRM и его правила либо описать его как штатный канал с
  ограничением по адресу. Это единственный `fail`;
- отсутствие egress-политики на Windows-цели — вопрос к дизайну, а не к узлу;
- OS-04 — выполнить регресс с перезагрузкой в согласованное окно. Без него
  утверждение «всё поднимается само» остаётся непроверенным.

Отдельно для планирования части 2: на этой машине сценарии с двумя
одновременными пользователями проверяемы только в пределах двух
административных сеансов (`LicensingType=1`, роль RD Session Host не
установлена), а учётных записей сотрудников нет — `Remote Desktop Users` пуста.

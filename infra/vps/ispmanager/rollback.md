# Откат

Правило: сначала возвращаем клиентские сайты, потом разбираемся с панелью.
Панель может подождать, чужие сайты — нет.

Каждый запуск `deploy-panel.sh` печатает путь к своей резервной копии:
`/var/backups/electerm-platform/<метка времени>/`. Внутри лежат копии файлов с
сохранением полных путей, снимки состояния и `RESTORE.txt` с командами,
подставленными под конкретный запуск. Если путь не сохранился:

```bash
ls -1t /var/backups/electerm-platform | head -n 5
```

## Быстрый откат: одна команда на шаг

| Что откатываем | Команда | Время | Влияние на клиентские сайты |
|---|---|---|---|
| Проксирование | `rm -f /etc/nginx/vhosts-resources/mql5.ink/10-electerm-panel.conf && nginx -t && systemctl reload nginx` | 5 с | нет |
| Приложение | `cd /opt/electerm-platform && docker compose down` | 15 с | нет |
| Приложение вместе с данными | `cd /opt/electerm-platform && docker compose down -v` | 20 с | нет, но данные панели теряются |
| Файлы приложения | `rm -rf /opt/electerm-platform` | 5 с | нет |
| Сети Docker нашего проекта | `docker network rm electerm-platform_internal` | 5 с | нет |

## Шаг 1. Проксирование

Единственное изменение, которое видно снаружи и способно задеть сайты, потому
что затрагивает конфигурацию веб-сервера.

```bash
rm -f /etc/nginx/vhosts-resources/mql5.ink/10-electerm-panel.conf
nginx -t && systemctl reload nginx
```

Файл конфигурации самого сайта мы не меняли, восстанавливать его не нужно.
Копия на случай сомнений лежит в каталоге резервной копии по тому же пути, что
и оригинал, например
`/var/backups/electerm-platform/<метка>/etc/nginx/vhosts/www-root/mql5.ink.conf`.
Сравнить:

```bash
diff -u /var/backups/electerm-platform/<метка>/etc/nginx/vhosts/www-root/mql5.ink.conf \
        /etc/nginx/vhosts/www-root/mql5.ink.conf
```

Если различия есть, а мы этот файл не трогали, значит его перегенерировала
панель — это нормально, восстанавливать копию не нужно и вредно.

Для Apache-варианта путь другой, а порядок тот же:

```bash
rm -f /etc/apache2/vhosts-resources/mql5.ink/10-electerm-panel.conf
apache2ctl configtest && systemctl reload apache2
```

**Порядок важен.** Сначала `nginx -t`, только потом `reload`. `reload` с битой
конфигурацией nginx не применяет — старые процессы продолжают работать, — но
`restart` в этой ситуации остановит все сайты. Поэтому `restart` при откате не
используется никогда.

## Шаг 2. Приложение

```bash
cd /opt/electerm-platform
docker compose down
```

Контейнеры останавливаются и удаляются, тома с данными остаются. Порт 5577
освобождается. Клиентские сайты не затрагиваются: приложение слушало только
loopback и не участвовало в обработке их трафика.

Полное удаление вместе с данными панели (машины, история, настройки):

```bash
docker compose down -v
```

Это необратимо. Делать только если данные заведомо не нужны.

## Шаг 3. Файлы приложения

Вернуть предыдущую версию, если каталог существовал до запуска:

```bash
cp -a /var/backups/electerm-platform/<метка>/opt/electerm-platform/. /opt/electerm-platform/
```

Удалить полностью:

```bash
rm -rf /opt/electerm-platform
```

В `.env` лежат секреты. Если каталог удаляется как ненужный, а не для
переустановки, секреты считаются раскрытыми и подлежат смене.

## Шаг 4. Образы Docker

Образы остаются на диске и занимают место, но ни на что не влияют. Удалять их
имеет смысл только если освобождается место:

```bash
docker image ls
docker image rm <идентификатор>
```

`docker system prune -a` на этом сервере **не запускать**: он удалит образы и
тома чужих контейнеров, если они есть.

## Шаг 5. Docker целиком

Актуально только если Docker устанавливался ради панели. `deploy-panel.sh` его
не ставит, поэтому это ручное решение и ручной откат.

```bash
systemctl stop docker docker.socket
systemctl disable docker docker.socket
```

Остановка демона оставляет за собой цепочки iptables `DOCKER`, `DOCKER-USER`,
`DOCKER-ISOLATION-*` и мост `docker0`. Сами по себе они трафик клиентских сайтов
не блокируют, но замусоривают правила. Удаление пакета:

```bash
apt-get remove --purge docker-ce docker-ce-cli containerd.io docker-compose-plugin
reboot   # только в согласованное окно: перезагрузка останавливает все сайты
```

Перезагрузка нужна, чтобы правила и мосты собрались заново с чистого состояния.
Без перезагрузки лишние цепочки останутся до конца жизни системы. Если окна нет
— оставьте демон установленным и выключенным, это безопаснее перезагрузки.

## Что откатить нельзя

| Действие | Почему необратимо | Как избежать |
|---|---|---|
| Установка Docker | цепочки iptables и мост создаются в ядре, чистое состояние возвращается только перезагрузкой | ставить в окно обслуживания, заранее сняв `iptables-save` |
| `a2enmod` + перезапуск Apache | перезапуск обрывает все текущие соединения сайтов | планировать окно; для nginx-варианта модуль не нужен |
| `webreconfigure` в панели | удаляет все ручные правки в конфигурации всех сайтов | не запускать; наш фрагмент его переживает |
| `docker compose down -v` | тома с данными панели удаляются | не использовать при откате «на время» |
| Изменение пула подсетей Docker | требует остановки демона и пересоздания сетей | задать один раз до создания сетей |
| Смена `SERVER_SECRET` | разлогинивает всех | менять только осознанно |

## Аварийные ситуации

### Клиентские сайты отдают 502 или 404 после наших действий

```bash
rm -f /etc/nginx/vhosts-resources/mql5.ink/10-electerm-panel.conf
nginx -t && systemctl reload nginx
```

Дальше проверить, что фрагмент был единственным изменением:

```bash
ls -la /etc/nginx/vhosts-resources/mql5.ink/
ls -lt /etc/nginx/vhosts/www-root/ | head
```

Наш фрагмент влияет только на `location /panel/` домена `mql5.ink`. Если после
его удаления сайты не поднялись, причина не в нём: смотреть журналы nginx и
недавние действия в панели.

### ISPmanager не открывается на 1500

Мы не меняем ни порт 1500, ни правила фаервола, поэтому наш комплект такой
ситуации не создаёт. Проверить:

```bash
systemctl status ihttpd
ss -lnt | grep 1500
iptables -S | grep 1500
```

Сравнить текущие правила со снимком `iptables-filter.txt` из каталога резервной
копии — он снят до изменений.

### Потерян доступ по SSH

Наш комплект не трогает sshd и фаервол. Если доступ потерян, причина внешняя:
`fail2ban` заблокировал адрес, правила панели изменились, провайдер. Путь
восстановления — консоль VPS у провайдера. Разблокировка адреса из консоли:

```bash
fail2ban-client set sshd unbanip <адрес>
```

### Приложение поднялось, но панель недоступна снаружи

Это не аварийная ситуация, сайты не затронуты. Проверять по порядку:

```bash
curl -sI http://127.0.0.1:5577/                    # приложение отвечает?
grep -r vhosts-resources /etc/nginx/vhosts/www-root/mql5.ink.conf   # include есть?
ls -la /etc/nginx/vhosts-resources/mql5.ink/       # фрагмент лежит?
nginx -T 2>/dev/null | grep -A5 'location ^~ /panel/'  # попал в рабочую конфигурацию?
tail -50 /var/www/httpd-logs/mql5.ink.error.log    # что говорит nginx
```

`nginx -T` печатает конфигурацию так, как её видит запущенный процесс. Если
фрагмента там нет, значит либо не было `reload`, либо `include` отсутствует.

# Аудит пакета `@electerm/electerm-react` 5.3.15

Дата: 2026-08-30
Режим: **только статический анализ**. `npm install`/`npm ci`/`npm pack` не запускались,
скрипты пакета, Node-код из пакета, shell-файлы и бинарники не исполнялись.
Машиночитаемый результат: [`security/manifests/electerm-react-5.3.15.json`](../../security/manifests/electerm-react-5.3.15.json).

## 0) Зачем этот аудит

`electerm-web` не содержит исходников браузерного UI: они подставляются из npm-пакета
`@electerm/electerm-react`. То есть весь код, который выполняется в браузере
пользователя — терминал, SFTP, закладки, AI-агент и MCP-инструменты, — приходит из
пакета, которого нет в дереве форка. Аудит цепочки поставок 2026-08-15
(`docs/audit/supply-chain.md`) закрыл версию 5.1.20 по внешним эндпоинтам, но не
разбирал браузерную поверхность атаки. Здесь разбирается версия 5.3.15 целиком.

блочное устройства, fifo, setuid и setgid — отбраковываются, а чистый архив
проходит без нарушений. Отдельно проверено, что инструмент отказывается писать
внутрь репозитория и принимать диапазон версий вместо точной. Повторный запуск
даёт тот же SHA-256 и те же 529 записей.

### Происхождение исходников: подтверждено до коммита

У пакета есть **SLSA provenance v1** и подпись реестра, и они сходятся с GitHub:

- `subject.digest.sha512` в аттестации равен вычисленному нами SHA-512 тарбола;
- `resolvedDependencies[0]` = `git+https://github.com/electerm/electerm@refs/tags/v5.3.15`,
  `digest.gitCommit` = `ba923cd412664ec5cd0b630548f74a7fc59069c8`;
- `gitHead` в npm-метаданных — тот же `ba923cd4...`;
- GitHub API `repos/electerm/electerm/git/ref/tags/v5.3.15` → `ba923cd4...`;
- `repository_id` 106087444 и `repository_owner_id` 32591856 из аттестации совпадают
  с `id`/`owner.id` репозитория в GitHub API;
- сборка — workflow `.github/workflows/electerm-react-publish.yml` по событию `release`
  на github-hosted runner, публикация через trusted publisher (OIDC), без токена

**Вывод: соответствие «версия ↔ репозиторий ↔ коммит» — высокой достоверности.**
Это редкий случай, когда npm-пакет можно привязать к конкретному коммиту не по
честному слову, а по подписанной аттестации.

### Что в поставке

- `install`/`preinstall`/`postinstall` — **нет вообще**, поля `scripts` в `package.json` нет.
- Зависимостей (`dependencies`, `peerDependencies`, `bundledDependencies`) — **нет**.
  Пакет отдаёт только исходники, сборку и зависимости обеспечивает потребитель.
- 529 записей tar, **все обычные файлы**. Симлинков, жёстких ссылок, устройств, fifo,
  абсолютных путей, `..`, букв дисков и setuid/setgid-битов — ноль.
- Классификация: 528 исходных файлов + 1 шаблон `client/views/index.pug`.
  **Минифицированного, сгенерированного и бинарного кода нет ни одного файла.**
  По расширениям: 299 `.jsx`, 165 `.js`, 60 `.styl`, по одному `.json`, `.md`, `.mjs`, `.pug`.

Отдельно стоит отметить: обычно в npm-пакете UI лежит собранный бандл, который
нечитаем и который приходится помечать как непроверяемый. Здесь этого нет — весь
код доступен для чтения, поэтому непроверяемых артефактов в пакете не осталось.

## 2) Контракт MCP: как рендерер связан с виджетом сервера

```
виджет mcp-server (main-процесс electerm-web)
   │  ipc-событие 'mcp-request' { requestId, action:'tool-call', data:{ toolName, args } }
   ▼
client/store/mcp-handler.js:59  handleMcpToolCall(requestId, toolName, args)
   │  switch по toolName -> store.mcp*(args)
   ▼
window.api.sendMcpResponse({ requestId, result | error })
```

Включается это в `client/store/widgets.js:20`: `runWidget('mcp-server')` вызывает
`store.initMcpHandler()`. То есть MCP-поверхность появляется ровно тогда, когда
запущен виджет с идентификатором `mcp-server`.

Рендерер обслуживает **43 имени инструментов**: закладки (6), группы закладок (2),
быстрые команды (4), вкладки (8), терминал (7), фоновые задачи (5), SFTP (4),
передача файлов (2), списки передач (2), zmodem (2), настройки (1).

Второй потребитель тех же обработчиков — встроенный AI-агент:
`client/components/ai/agent-tools.js:448` `executeToolCall` вызывает те же самые
`store.mcp*` методы. **Backend исполнения у MCP-виджета и у AI-чата общий**, поэтому
любой дефект в `mcp-handler.js` достижим с обеих сторон, в том числе через вывод
терминала, попавший в контекст модели (prompt injection → вызов инструмента).

### Три расхождения контракта

1. **Схемы аргументов в пакете отсутствуют.** JSON-схемы объявляет виджет
   `mcp-server` на стороне main-процесса, в аудируемом пакете их нет. Внутри пакета
   схемы есть только для агента (`agent-tools.js`) и покрывают 25 имён из 43.
   Оставшиеся 18 не валидируются ничем внутри границы аудита — и рендерер тоже
   не валидирует аргументы сам. Именно поэтому находки ER-02 и ER-03 ниже ничем
   не перекрыты.
2. **Четыре инструмента объявлены, но не реализованы.** Ветки `switch` для
   `list_quick_commands`, `add_quick_command`, `run_quick_command`,
   `delete_quick_command` (`mcp-handler.js:95-104`) вызывают методы, реализации
   которых закомментированы (`mcp-handler.js:357-408`). Любой вызов даёт `TypeError`,
   который перехватывается и возвращается как `error`.
3. **Guardrails — только текст промпта.** `ai-guardrails.js:4-10` дописывает
   `window.et.mandatoryGuardrails` в системную роль. Это не технический контроль
   вызова инструментов, и полагаться на него как на границу безопасности нельзя.

## 3) Находки

Полный перечень с местами и вердиктами — в манифесте. Ниже разбор по существу.

### ER-01. Чтение системного буфера обмена по команде удалённого хоста (high)

`client/components/terminal/osc52-addon.js:37` регистрирует обработчик OSC 52
безусловно, а `:70` и `:83-93` реализуют **запрос на чтение**: при появлении в потоке
терминала последовательности `ESC]52;c;?BEL` клиент вызывает `window.pre.readClipboard()`
и отправляет содержимое буфера обратно в PTY.

Опасно это тем, что поток терминала контролирует удалённая сторона. Достаточно
скомпрометированного сервера, `cat` вредоносного файла или подготовленного вывода
любой команды — и буфер обмена пользователя (куда регулярно попадают пароли и токены)
уезжает на хост. Ни настройки, ни запроса подтверждения, ни списка доверенных хостов
в коде нет. Ровно по этой причине чтение OSC 52 по умолчанию выключено в xterm и
большинстве терминалов.

**Вердикт: вырезать путь чтения.** Запись в буфер (`_handleWriteRequest`) полезна и
может остаться, но за явной настройкой.

### ER-02. Инъекция команд через «читающий» инструмент `get_background_task_log` (high)

`client/store/mcp-handler.js:1060-1062`:

```js
const lines = args.lines || 100
const output = await runMonitorCmd(task.tabId,
  `tail -n ${lines} ${task.logFile} 2>/dev/null || echo '(no output yet)'`)
```

`args.lines` не приводится к числу и не проверяется, а подставляется в строку команды.
Значение вида `1 /etc/shadow; <произвольная команда> #` даёт выполнение на удалённом
хосте. Важно не то, что MCP и так умеет выполнять команды, а то, что `get_background_task_log`
выглядит как read-only инструмент: развёртывание, разрешившее только «безопасные»
инструменты, получит через него полноценное исполнение.

**Вердикт: `Number.parseInt` с диапазоном.**

### ER-03. Инъекция команд через имена файлов в `zmodem_download` (high)

`client/store/mcp-handler.js:1372-1373`:

```js
const quotedFiles = remoteFiles.map(f => `"${f}"`).join(' ')
term.runQuickCommand(`${downloadCmd} ${quotedFiles}`)
```

Двойные кавычки в POSIX-оболочке не защищают от подстановки команд и раскрытия
переменных: `$(...)`, обратные кавычки и `${...}` внутри двойных кавычек
интерпретируются. Имя файла, содержащее такую конструкцию, выполняется.

**Вердикт: одинарные кавычки с экранированием либо белый список символов пути.**

### ER-04. Блок-лист опасных свойств применяется не везде (high)

В `mcp-handler.js:26-43` объявлен `dangerousTabProps` (`execLinux`, `execMac`,
`execWindows`, `*Args`, `setEnv`, `runScripts`, `interactiveValues`) и функция
`stripDangerousTabProps`. Комментарий прямо говорит, что эти свойства дают
произвольное исполнение команд.

Фильтр применён **только** в `mcpOpenTab` (`:527`). А `mcpAddBookmark` (`:267-286`)
и `mcpEditBookmark` (`:288-303`) передают `args`/`updates` дальше без фильтрации.
Отсюда обход в два шага: `add_bookmark` (или `edit_bookmark`) сохраняет закладку с
`runScripts`/`execLinux`/`setEnv`, затем `open_bookmark` её открывает и свойства
срабатывают. Блок-лист `open_tab` при этом не задействован.

**Вердикт: применять `stripDangerousTabProps` во всех трёх местах.**

### ER-05. XSS в origin приложения через web-вкладку (high)

Складывается из трёх слабых мест:

1. `client/components/bookmark-form/fix-bookmark-default.js:90-111` —
   `validateBookmarkData` проверяет только непустоту обязательных полей
   (`if (!data[field])`). Для `type: 'web'` обязателен один `url`, и никакой
   проверки схемы URL нет.
2. `client/components/web/web-session.jsx:13` —
   `const urlRegex = /^[a-z\d.+-]+:\/\/[^\s/$.?#].[^\s]*$/i`. Регулярка требует
   `схема://`, поэтому простой `javascript:alert(1)` не проходит. Но схема
   `javascript` с двумя слэшами и последующим переносом строки в процентной
   кодировке шаблону соответствует: `//` становится комментарием, а код после
   перевода строки исполняется.
3. `client/components/web/web-session.jsx:105-116` — в веб-режиме
   (`window.et.isWebApp`, то есть в нашей целевой поставке) рендерится
   `<iframe src={url}>` **без атрибута `sandbox`**, без `referrerPolicy` и без `allow`.

`javascript:`-URL в `src` фрейма исполняется в origin встраивающего документа, то
есть получает доступ к приложению целиком: закладки, токен сессии, WebSocket.
Цепочка достижима из MCP: `open_tab` с `type: 'web'` создаёт такую вкладку.

**Вердикт: web-вкладки вырезать.** Браузер внутри терминального клиента для нашего
сценария не нужен, а чинится это иначе — белым списком схем (`http`/`https`),
`sandbox` и CSP.

### ER-06. Обход нативных диалогов выбора файла через тестовые хуки (high)

`client/components/terminal/transfer-client-base.js:179-180` документирует
`window._apiControlSelectFile` дословно как средство e2e-тестирования: «Set
`window._apiControlSelectFile = [...]` to bypass native dialog». То же для
`_apiControlSelectFolder` (`:228-235`).

`mcp-handler.js:1323` и `:1366` выставляют эти же переменные в продакшн-пути
MCP-инструментов `zmodem_upload`/`zmodem_download`. В результате вызов инструмента
отправляет произвольные локальные файлы (`~/.ssh/id_rsa`, база настроек с
сохранёнными паролями) на удалённый хост **без диалога и без участия пользователя**.
Диалог выбора файла здесь был единственным местом, где пользователь подтверждал
передачу.

**Вердикт: тестовые хуки убрать из продакшн-пути; MCP-передача файлов только через
явное подтверждение либо белый список каталогов.**

### ER-08. «Шифрование» localStorage, которого нет (high)

`client/common/safe-local-storage.js:23-55`: `encrypt` — это XOR повторяющимся ключом
плюс base64 с префиксом `enc1:`. Это обфускация, а не шифрование: при известном или
угадываемом фрагменте открытого текста ключ восстанавливается тривиально.

Хуже другое (`:101-132`): все «безопасные» функции начинаются с

```js
if (window.et.isWebApp) {
  return setItem(id, str)
}
```

То есть **в браузерной поставке — той самой, ради которой берётся этот пакет, —
`safeSetItem` вырождается в обычный `localStorage.setItem` открытым текстом.**
Любой XSS (см. ER-05) читает эти значения напрямую.

**Вердикт: заменить на реальную схему хранения; в браузере не хранить секреты в
`localStorage` вовсе.**

### ER-09. `ws://` с токеном в query-строке (high)

`client/entry/worker.js:15`:

```js
const wsUrl = `ws://${host}:${port}/${type}/${id}?&sftpId=${sftpId}&token=${tokenElecterm}`
```

Тот же шаблон в `terminal/terminal.jsx:1794`, `rdp/rdp-session.jsx:125`,
`vnc/vnc-session.jsx:104`, `spice/spice-session.jsx:122`. Две проблемы сразу:
схема `ws://` без TLS и сессионный токен в URL. Токен в query-строке оседает в
логах обратного прокси и сервера, а под HTTPS-страницей `ws://` — это ещё и
mixed content, который браузер заблокирует.

**Вердикт: `wss://` и перенос токена из URL в заголовок или в сообщение после
установления соединения.**

### ER-16. `disablewebsecurity` в десктопной ветке web-вкладок (high)

`client/components/web/web-session.jsx:125-128` задаёт для `webview`
`disablewebsecurity: 'true'` и `allowpopups: 'true'`, то есть отключает политику
одного источника. В браузерной поставке эта ветка не выполняется, но код лежит в
том же файле и остаётся при вендоринге.

**Вердикт: вырезать вместе с web-вкладками (ER-05).**

### Находки среднего и низкого уровня

- **ER-07** (`:1216`, `:1261`) — `conflictPolicy` по умолчанию `mergeOrOverwriteAll`:
  MCP-передача перезаписывает файлы на обеих сторонах без вопросов.
- **ER-10** (`:975-983`) — фоновые задачи пишут в предсказуемые
  `/tmp/electerm-bg-<время>-<счётчик>.{log,pid,exit}`. На многопользовательском хосте
  локальный злоумышленник заранее создаёт симлинк по угадываемому имени и получает
  перезапись чужого файла при перенаправлении вывода.
- **ER-11** (`:981`) — `btoa(args.command)` бросает `InvalidCharacterError` на любых
  не-Latin1 символах, то есть `run_background_command` ломается на кириллице.
- **ER-13** — дефолтные внешние эндпоинты: 16 AI-провайдеров
  (`ai-config-props.js:17-129`), `https://api.atlascloud.ai/v1`
  (`default-setting.js:69`), облачный sync `https://sync.electerm.org/api/sync`
  (`setting-sync-form.jsx:70`), три зеркала обновлений (`update-check.js:77-83`) и
  Gitee-канал (`constants.js:206`). Подтверждает и уточняет F-08/F-09/F-10 прошлого
  аудита уже для 5.3.15.
- **ER-14** (`custom-css.jsx:16-17`) — санитайзер пользовательского CSS вырезает
  ровно одну подстроку `@import`. Обращения по `url()` и селекторы по атрибутам
  остаются, а это рабочий канал утечки данных из CSS.
- **ER-15** (`:1120-1129`) — `get_settings` отдаёт конфигурацию по списку исключений
  (`apiKeyAI`, `syncSetting`). Любое новое чувствительное поле автоматически станет
  доступно AI и MCP.
- **ER-18** (`:1173-1181`, `:1204-1247`) — `sftp_read_file`/`sftp_upload` по
  назначению работают с произвольными путями; ограничение вводится политикой, а не
  кодом пакета.
- **ER-19** (`ai-guardrails.js:4-10`) — guardrails только на уровне промпта.

## 4) Что в пакете оказалось чисто

Это важно зафиксировать не меньше находок:

- **нет** `eval()`, `new Function()`, `Function("...")`;
- **нет** `child_process`, `document.write`, `insertAdjacentHTML`, `XMLHttpRequest`,
  `window.open`, `document.domain`, `window.opener`;
- **нет** телеметрии и аналитики: ни одного безусловного исходящего запроса при
  старте, все внешние адреса включаются только явными функциями;
- **нет** обфусцированных или скрытых полезных нагрузок: минифицированного и
  сгенерированного кода в пакете нет вообще;
- 24 вызова динамического `import()` — статические литеральные пути (code splitting),
  пользовательский ввод в них не попадает;
- `dangerouslySetInnerHTML` ровно один (`sys-menu/menu-btn.jsx:206`) и вставляет
  статический SVG-логотип из модуля, а не данные;
- пять присваиваний `innerHTML` — все пишут CSS внутрь тегов `<style>`, HTML не
  вставляется (риск ограничен CSS-инъекцией, см. ER-14);
- `sanitizeBookmark` (`mcp-handler.js:242-252`) корректно вырезает `password`,
  `privateKey`, `passphrase`, `certificate`, `proxy`, `connectionHoppings`,
  `sshTunnels` из выдачи `list_bookmarks`/`get_bookmark`, заменяя их флагами
  `hasXxx` — секреты закладок в AI и MCP не утекают;
- `mcpExecuteCommand` аккуратно ограничивает таймаут (`1..600` секунд) и объём
  вывода, а PTY-обёртка запускает команду в подоболочке, чтобы `exit`/`exec` не
  убили внешний shell.

Наличие `dangerousTabProps` и `sanitizeBookmark` показывает, что автор осознанно
занимался безопасностью MCP-слоя. Находки ER-02/ER-03/ER-04 — это пропуски в уже
выбранном подходе, а не отсутствие подхода.

## 5) Что блокирует вендоринг и что нужно сделать

Лицензия MIT вендорингу не мешает, происхождение подтверждено, поставка чистая.
Блокируют дефекты браузерной поверхности. Минимальный набор правок, **сохраняющий

1. `osc52-addon.js` — удалить `_handleReadRequest` и ветку `payload === '?'`
   (`:70-72`, `:83-93`); запись оставить за настройкой. *(ER-01)*
2. `mcp-handler.js:1060` — `const lines = Math.min(Math.max(parseInt(args.lines, 10) || 100, 1), 10000)`. *(ER-02)*
3. `mcp-handler.js:1372` — экранировать пути одинарными кавычками

   `stripDangerousTabProps`, как это уже делает `mcpOpenTab`. *(ER-04)*
5. Удалить `components/web/*` и ветку `type: 'web'` из схемы закладок; убрать
   `web` из `bookmarkSchema`/`requiredFields`. *(ER-05, ER-16)*
6. `mcp-handler.js:1323`, `:1366` — убрать использование `_apiControlSelectFile`
   и `_apiControlSelectFolder`; для MCP-передачи ввести подтверждение или белый

7. `mcp-handler.js:1216`, `:1261` — сменить дефолт `conflictPolicy` на
   запрашивающий, перезапись только явным аргументом. *(ER-07)*
8. `safe-local-storage.js` — убрать XOR как «шифрование» и не хранить секреты в
   `localStorage` в веб-режиме. *(ER-08)*
9. Транспорт — `wss://`, токен вне query-строки, во всех пяти местах. *(ER-09)*
10. `mcp-handler.js:975` — непредсказуемые имена временных файлов
    (`mktemp`) вместо шаблона со счётчиком. *(ER-10)*

затрагивают экранирование, валидацию, дефолты и транспорт.

## 6) Чего проверить не удалось

Честный список пробелов важнее видимости полного покрытия.

1. **Построчное чтение всех 529 файлов не выполнялось.** Полностью прочитаны
   12 файлов: `store/mcp-handler.js` (1385 строк), `store/widgets.js`,
   `components/ai/agent-tools.js` (маршрутизация и схемы), `components/ai/ai-guardrails.js`,
   `common/safe-local-storage.js`, `entry/worker.js`, `components/terminal/osc52-addon.js`,
   `components/bg/custom-css.jsx`, `components/web/web-session.jsx`,
   `components/bookmark-form/fix-bookmark-default.js`, `package.json`, `LICENSE`.
   Остальные 517 покрыты сплошным шаблонным поиском по URL и по списку опасных API
   и хешированы поштучно, но построчно не прочитаны. Скрытая логика в необследованном
   файле, не использующая ни одного искомого шаблона, этим методом не ловится.
2. **Подпись аттестации криптографически не проверялась.** Sigstore/Fulcio-верификация
   требует внешнего верификатора, а запуск стороннего исполняемого кода правилами
   аудита запрещён. Проверено содержимое аттестации и его согласованность с GitHub API,
   но не сама подпись.
3. **Побайтового сравнения тарбола с деревом репозитория на коммите `ba923cd` нет.**
   Пакет собирается из подкаталога исходников `electerm`, соответствие путей 1:1 не
   подтверждалось. Уверенность в происхождении опирается на аттестацию, а не на диф.
4. **Воспроизводимость сборки не проверялась** — потребовался бы запуск чужого
   pipeline.
5. **Схемы MCP-инструментов вне границы аудита.** 18 из 43 имён не имеют схемы ни в
   рендерере, ни в `agent-tools.js`; их объявляет виджет `mcp-server` в main-процессе.
   Насколько там валидируются аргументы (и перекрываются ли ER-02/ER-03), по этому
   пакету установить нельзя — нужен отдельный аудит серверной части `electerm-web`.
6. **Достижимость ER-05 подтверждена по коду, но не воспроизведением.** Цепочка
   «`open_tab` → `type: 'web'` → `urlRegex` → `iframe src`» прослежена статически;
   исполняемой проверки не делалось, потому что она означала бы запуск чужого кода.
7. **Транзитивные зависимости не рассматривались** — их у пакета попросту нет,
   но собранное приложение получит их из `package-lock.json` форка, и это предмет
   отдельной проверки.

# Контрольный список перед применением

Сервер `202.155.8.133` обслуживает десятки клиентских сайтов. Их простой —
единственный по-настоящему недопустимый исход. Панель платформы может не
заработать, может заработать позже, может работать на неудобном адресе; всё это
приемлемо. Остановка чужих сайтов или потеря доступа к ISPmanager — нет.

## 0. Главный запрет

**Не запускайте на этом сервере `infra/vps/setup-server.sh`.** Он написан под
чистую Ubuntu и делает следующее:

- `ufw --force reset`, `ufw default deny incoming`, `ufw default deny outgoing`,
  открыт только 22 и 51820 — порты 80, 443 и 1500 закрываются. Это
  одновременная остановка всех клиентских сайтов и потеря доступа к панели
  ISPmanager. Восстановление — только через консоль провайдера;
- установка Docker с созданием цепочек iptables и моста `docker0` в системе,
  где правилами может управлять панель;
- `fail2ban` с агрессивным режимом для sshd — при неудачных попытках блокирует
  адрес администратора;
- `unattended-upgrades` — неконтролируемые обновления на чужом продакшне.

Комплект в этом каталоге — отдельный путь для сервера с панелью. Он не ставит
пакеты, не трогает фаервол и не перезапускает веб-сервер.

## 1. Что нужно иметь на руках до начала

- Доступ к консоли VPS у провайдера (VNC или аналог). Это единственный путь
  восстановления, если доступ по сети будет потерян. Без него начинать нельзя:
  проверять наличие консоли в момент аварии — поздно.
- Второй канал в панель ISPmanager: работающая сессия в браузере, открытая
  заранее. Если что-то пойдёт не так с сетью, действующая сессия может
  остаться живой.
- Согласованное окно на случай, если понадобится перезагрузка или перезапуск
  Apache. Само развёртывание окна не требует, но соседние решения (установка
  Docker, включение модулей Apache) — требуют.
- Отчёт `inventory.sh`, снятый не более чем за сутки до применения.

Проверяется по отчёту `inventory.sh`. Пункт без ответа — стоп, не догадка.

## 3. Классификация шагов по риску

### Безопасно: не влияет на клиентские сайты

- `inventory.sh` — только чтение;
- `deploy-panel.sh --dry-run` — ничего не меняет;
- `docker compose pull` — загрузка образов, влияет только на место на диске;
- `docker compose up -d` с публикацией на 127.0.0.1 — новый слушатель на
  loopback, чужой трафик не затрагивает;
- запись фрагмента в каталог ресурсов домена **без** `reload` — файл лежит, но
  не действует.

### Требует внимания: обратимо, но видно снаружи

- `nginx -t` — читает конфигурацию; может создать отсутствующий файл журнала,
  других изменений не делает;
- `systemctl reload nginx` — graceful, установленные соединения не рвутся,
  сайты не останавливаются. Но если конфигурация битая, `reload` её просто не
  применит, а вот `restart` в этот момент остановит всё. Поэтому `restart`
  веб-сервера в этом комплекте не используется никогда;
- создание сети Docker — при пересечении подсетей может перехватить трафик,
  проверяется до создания.

### Необратимо

- установка Docker: цепочки iptables и мост создаются в ядре, чистое состояние
  возвращает только перезагрузка;
- `a2enmod` с перезапуском Apache: перезапуск обрывает все соединения сайтов;
- `webreconfigure` в панели: удаляет все ручные правки конфигурации всех
  сайтов;
- `docker compose down -v`: удаляет тома с данными панели;
- `docker system prune -a`: удаляет чужие образы и тома.

### Способно отрезать доступ к серверу или к панели ISPmanager

Ни одно из этих действий комплект не выполняет. Список нужен, чтобы никто не
сделал их «попутно»:

| Действие | Что произойдёт |
|---|---|
| `ufw enable` с политикой deny incoming | закрываются 80, 443, 1500, 22 — сайты и панель недоступны |
| `ufw --force reset` | снимаются действующие разрешающие правила |
| Смена порта или адреса прослушивания ISPmanager | панель недоступна на 1500 |
| Правка `iptables -P INPUT DROP` без разрешения 22 и 1500 | потеря SSH и панели немедленно |
| `systemctl restart nginx` при битой конфигурации | все сайты отдают ошибку до исправления |
| Перезагрузка сервера | простой всех сайтов; после неё сервисы могут не подняться, если автозапуск не проверен |
| Запуск `setup-server.sh` | всё перечисленное сразу, см. раздел 0 |

## 4. Порядок действий

Порядок выбран так, чтобы каждое следующее действие делалось только после
подтверждения предыдущего, и чтобы самое рискованное было последним и
наименьшим.

1. **Инвентаризация.** `sudo ./inventory.sh > inventory.txt` на сервере, отчёт
   забрать себе. Ответить на все 13 пунктов чек-листа.
2. **Решение про Docker.** Если Docker не установлен — остановиться. Установка
   планируется отдельно, в окно обслуживания, с предварительным
   `iptables-save > /root/iptables-before-docker.rules` и планом отката.
   `deploy-panel.sh` намеренно не делает этого сам.
3. **Сухой прогон.** `sudo ./deploy-panel.sh --dry-run` и
   `sudo ./deploy-panel.sh --dry-run --with-proxy nginx`. Прочитать план
   целиком, включая текст фрагмента, который будет записан.
4. **Приложение без проксирования.** `sudo ./deploy-panel.sh`. На этом шаге
   панель работает и доступна только с самого сервера
   (`curl -sI http://127.0.0.1:5577/`). Снаружи не изменилось ничего. Здесь же
   проверяется, что клиентские сайты по-прежнему открываются.
5. **Фрагмент проксирования без перечитывания.**
   `sudo ./deploy-panel.sh --with-proxy nginx`. Скрипт делает копию, пишет
   фрагмент, выполняет `nginx -t` и снимает фрагмент, если проверка не прошла.
   `reload` не выполняется.
6. **Перечитывание конфигурации.** `nginx -t && systemctl reload nginx`. Сразу
   после — открыть два-три клиентских сайта и убедиться, что они работают.
7. **Проверка панели снаружи.** Открыть `https://mql5.ink/panel/`, войти,
   открыть терминал и оставить его на пять минут без ввода. Если соединение
   рвётся — дело в таймаутах или в WebSocket, см. `reverse-proxy.md`.
8. **Фиксация.** Записать в `docs/design/environments.md` фактическое состояние
   сервера по отчёту инвентаризации, чтобы следующий раз не начинался с
   догадок.

Шаги 4 и 5 сознательно разделены: так при появлении проблемы сразу видно, в чём
причина — в приложении или в конфигурации веб-сервера.

## 5. Стоп-сигналы

Прекратить работу и не продолжать, если:

- `inventory.sh` не нашёл `include` каталога ресурсов в конфигурации домена;
- Docker отсутствует, а окна обслуживания на его установку нет;
- `nginx -t` не проходит **до** наших изменений: значит, конфигурация уже
  сломана, и любое перечитывание остановит сайты. Это отдельная проблема
  владельца сервера, и трогать её нашими руками нельзя;
- порт 5577 занят посторонним процессом;
- в отчёте видно, что правилами iptables управляет панель, а вам нужно открыть
  порт (Вариант Б в `reverse-proxy.md`): открытие порта в этом случае
  согласуется с владельцем;
- на диске меньше 3 ГБ свободного места;
- обнаружены переопределённые шаблоны панели, и вы не знаете, кто и зачем их
  правил.

## 6. Проверка после применения

Ни один пункт не пропускать. Первые два важнее остальных.

```bash
# 1. Клиентские сайты живы (подставить два-три реальных домена)
for d in site1.example site2.example; do
  printf '%s -> ' "$d"
  curl -sS -o /dev/null -w '%{http_code}\n' --max-time 10 "https://${d}/"
done

# 2. Панель ISPmanager отвечает
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 10 -k https://127.0.0.1:1500/

# 3. Приложение отвечает на loopback
curl -sI --max-time 5 http://127.0.0.1:5577/ | head -n 1

# 4. Порт приложения не виден снаружи: только 127.0.0.1
ss -lnt | grep 5577

# 5. Фрагмент попал в рабочую конфигурацию nginx
nginx -T 2>/dev/null | grep -c 'location \^~ /panel/'

# 6. Наружу открыты только ожидаемые порты
ss -lnt | grep -E '0\.0\.0\.0|\[::\]'
```

Пункт 4 — принципиальный. Docker публикует порты через собственные цепочки
iptables, которые обрабатываются раньше правил ufw и панели, поэтому
опубликованный на все интерфейсы порт не закрывается фаерволом. Привязка к
`127.0.0.1` — не косметика, а единственное, что здесь реально работает.

## 7. Риски для клиентских сайтов и как каждый снимается

| Риск | Как снимается в этом комплекте |
|---|---|
| `setup-server.sh` закроет порты и оборвёт сайты | отдельный скрипт, который не трогает фаервол; предупреждение в заголовке скрипта и в разделе 0 |
| Правка конфигурации будет затёрта панелью, и панель отвалится в случайный момент | используется каталог ресурсов домена, который панель не перезаписывает; `deploy-panel.sh` останавливается, если `include` этого каталога в конфигурации отсутствует |
| Ошибка в фрагменте сломает конфигурацию nginx и уронит все сайты при следующем перечитывании | `nginx -t` выполняется до `reload`, при неудаче фрагмент снимается автоматически; `reload` только по явному флагу |
| Приложение займёт 80 или 443 | публикация только на `127.0.0.1:5577`, скрипт проверяет compose на публикацию 80, 443, 1500 и на порты без привязки к loopback |
| Docker перепишет правила iptables и изменит обработку трафика | Docker не устанавливается скриптом; состояние iptables снимается в резервную копию до изменений; проверка занятости портов и пересечения подсетей до создания сетей |
| Новая сеть Docker перехватит трафик существующей подсети | проверка маршрутов в диапазонах пулов Docker, остановка при пересечении |
| Перезапуск веб-сервера оборвёт соединения сайтов | `restart` не используется нигде, только `reload`/`graceful`; для Apache отсутствующие модули не включаются автоматически |
| Заполнение диска образами остановит сайты и базы | проверка свободного места до `docker compose pull` |
| Невозможно быстро вернуться назад | резервная копия с полными путями и `RESTORE.txt` создаются до первого изменения, путь печатается в начале работы |
| Панель окажется доступна по http без шифрования | редирект на https внутри фрагмента, не полагаясь на настройки домена |
| Панель попадёт в поисковый индекс | `X-Robots-Tag: noindex` в фрагменте |

## 8. Что остаётся незакрытым

Честно перечислено, чтобы не выглядело закрытым:

- Общий пароль стокового `electerm-web` остаётся единственной проверкой
  личности, пока `mql5.ink` работает без Cloudflare Access. Домен обслуживается
  напрямую, не в зоне Cloudflare, поэтому Access к нему не применить. Панель на
  подпути — временная дверь; постоянная — целевой домен через туннель.
- Прямой доступ к `127.0.0.1:5577` с самого сервера обходит любые ограничения,
  наложенные на уровне nginx. Любой процесс на сервере, включая процессы чужих
  сайтов и их PHP-обработчики, может обратиться к приложению. Это довод в
  пользу того, что проверка личности обязана выполняться самим приложением.
- Установка Docker на этот сервер остаётся неоценённым риском до тех пор, пока
  не снят отчёт инвентаризации по фаерволу.
- Работоспособность нашей сборки за обратным прокси на подпути не проверена и
  проверяема только опытным путём.

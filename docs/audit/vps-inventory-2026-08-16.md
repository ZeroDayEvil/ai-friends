## 1. Как получен доступ

Штатный `ssh.exe` на Windows не принимает пароль из неинтерактивной оболочки,
поэтому первичный вход по паролю выполнен из одноразового Docker-контейнера с
`openssh-client` и `sshpass`. Образ закреплён по digest:
`alpine@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc`.
Пароль передавался только через переменную окружения контейнера (`-e SSHPASS`),
в командную строку не подставлялся. Контейнер запускался с `--rm`, на хосте
ничего не осталось.

В `~/.ssh/authorized_keys` root добавлена ровно одна строка — публичный ключ
`vps-anubis-2026-08-16` (идемпотентно, с проверкой на дубль). Права на файл
`0600`, владелец root. `sshd_config` не изменялся, вход по паролю намеренно
оставлен включённым.

Проверка входа по ключу без пароля:

```
ssh -i C:\remote-access\ssh\vps_ed25519 -o BatchMode=yes root@202.155.8.133 hostname
-> srv880044409
ssh vps hostname
-> srv880044409
```

В `C:\Users\root\.ssh\config` добавлен алиас `vps` по образцу `winsrv`.

## 2. Правка нашего скрипта

В `infra/vps/ispmanager/inventory.sh` строка 80 (`printf '--- (показано ...)'`)
падала с ошибкой `printf: --: invalid option`: формат, начинающийся с `--`,
трактуется как опция. Исправлено на `printf -- '--- ...'`. Ошибка была
косметической (не выводился «хвост» у листингов файлов), собранные данные не
пострадали. В приложенном логе следы этой ошибки видны — лог сохранён как есть,
без ретуши; правка касается будущих запусков.

## 5. Риски и что нельзя делать на этом сервере

- **Файрвол под управлением панели.** iptables/nft ведёт ISPmanager
  (`ispmgr_*`). Любые ручные правки iptables/nft недолговечны и опасны: ошибка
  может отрезать SSH или закрыть 80/443 для всех сайтов. Не трогать.
- **fail2ban на sshd.** Серия неудачных входов забанит наш IP (один адрес уже в
  бане). Мы перешли на ключ и `BatchMode` — риск низкий, но пароль перебирать
  нельзя.
- **Нет swap, ограниченная память.** 5.9 GB ОЗУ, свободно ~4.2 GB, swap = 0.
  Тяжёлые процессы (Docker + наше приложение) будут конкурировать за память;
  риск OOM, который заденет клиентские сайты. Перед развёртыванием — согласовать
  с владельцем добавление swap либо лимиты.
- **Конфигурация веб-сервера генерируется панелью.** Прямые правки файлов
  `vhosts/*.conf` теряются при перегенерации, продлении сертификата или
  изменении домена. Допустимо только через `vhosts-resources/<домен>/` (см.
  reverse-proxy.md, вариант А).
- **DNS-сервер боевой.** PowerDNS обслуживает 10 зон, включая клиентские и
  `hydradns.click`. Любой перезапуск/переконфигурация pdns — риск отказа DNS
  для многих доменов. Не трогать.
- **Один пользователь на все сайты.** Все сайты принадлежат `www-root`; изоляции
  между сайтами по пользователю нет. Компрометация одного сайта затрагивает все.
- **Сертификаты продлевает панель.** Наш проксирующий фрагмент должен ссылаться
  на те же пути cert/key, что и сайт (как в текущем nginx-конфиге), иначе
  продление сломает нашу настройку. Оба сертификата действуют до 04.11.2026.
- **Целевые каталоги пусты.** `mql5.ink` — заглушка (1 пустой файл),
  `vpn-service-api.pro` — пустой каталог. Приложение на `127.0.0.1:5577` не
  запущено. Развёртывание — «с нуля», но vhost'ы уже проксируют в Apache.
- **Характер размещаемых доменов.** Имена зон и сайтов

  оценку правовых и репутационных рисков размещения нашей панели рядом. Решение

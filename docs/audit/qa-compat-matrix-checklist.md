# Чек-лист матрицы совместимости

Исполнимый чек-лист для прогона платформы удалённого доступа на Windows 10,
Windows 11, Windows Server 2016, 2019, 2022 и 2025. Составлен так, чтобы прогон
мог выполнить человек, не участвовавший в разработке, и чтобы результат нельзя
было истолковать двояко.

Главная задача документа — не перечислить проверки, а заранее развести дефекты
платформы и штатные ограничения операционной системы. Без этого разделения отчёт
превращается в список «не работает», в котором половина пунктов исправлению не
подлежит.

## Как пользоваться

1. Подготовить машину по разделу «Предусловия», зафиксировать её параметры в
   журнале прогона.
2. Выполнять сценарии в порядке номеров: следующие опираются на предыдущие
   (пока не работает SSH, нет смысла проверять передачу файлов).
3. Для каждого пункта записать статус, фактическое поведение и, при отклонении,
   команды или шаги, которыми оно получено.
4. При отклонении сначала выполнить контрольный опыт из пункта «Как отличить
   дефект от ограничения ОС», и только потом присваивать `fail`.

Статусы: `pass` — соответствует ожидаемому; `fail` — дефект платформы;
`limit` — штатное ограничение ОС, поведение ожидаемо и не подлежит исправлению;
`blocked` — проверить не удалось, указать причину; `n/a` — сценарий к этой ОС не
применим.

**Правило контрольного опыта.** Почти для каждого сценария есть нативный
эквивалент: `mstsc` для RDP, `ssh` из командной строки, штатный VNC-клиент,
`scp`, буфер обмена внутри RDP-сеанса. Если нативный путь работает, а через
платформу — нет, это дефект платформы. Если не работает и нативный путь, это
ограничение или настройка ОС, и вести его нужно как `limit` с обоснованием.

## Ключевое различие: сколько одновременных сеансов допускает ОС

Это источник большинства ложных дефектов, поэтому оно вынесено до сценариев.

| Тип системы | Одновременные интерактивные сеансы | Что происходит со вторым пользователем |
|---|---|---|
| Windows 10, Windows 11 (клиентские) | один | Второй вход вытесняет первого. Windows показывает предупреждение о том, что другой пользователь работает, и при подтверждении первый сеанс отключается. Это свойство лицензирования клиентской Windows, а не ошибка. |
| Server 2016/2019/2022/2025 без роли RD Session Host | два административных | Третье подключение отклоняется с сообщением о превышении числа подключений. Штатное поведение режима удалённого администрирования (`LicensingType=1`). |
| Server 2016/2019/2022/2025 с ролью RD Session Host | много | Пользователи работают параллельно и не видят друг друга. Требуется сервер лицензий и CAL: без них через 120 дней льготного периода подключения перестанут приниматься. |

Формулировка для отчёта: на клиентских ОС вытеснение первого пользователя
вторым — `limit`. Дефектом является не вытеснение, а то, как платформа его
обрабатывает: молчаливый обрыв без объяснения, чёрный экран вместо сообщения,
зависший сеанс в интерфейсе, который на самом деле уже завершён, и тем более
показ содержимого чужого сеанса.

## Особенности систем, которые заранее известны

| ОС | Что учесть при прогоне |
|---|---|
| Windows 10 | OpenSSH Server как компонент Windows доступен начиная с версии 1809; на более ранних сборках его ставят из релиза Win32-OpenSSH. Один активный сеанс. Роль RD Session Host недоступна. |
| Windows 11 | То же по сеансам. Обновлённый стек RDP, динамическое изменение разрешения поддерживается. |
| Server 2016 | OpenSSH Server в компонентах Windows отсутствует, нужна установка из релиза Win32-OpenSSH. Стек RDP старше: часть возможностей изменения разрешения и перенаправления может отсутствовать. `Get-WindowsOptionalFeature`/`Add-WindowsCapability` для OpenSSH здесь неприменимы. |
| Server 2019 | OpenSSH Server доступен как компонент. Базовая система для сравнения. |
| Server 2022 | Дополнительно доступны настройки жёсткой политики блокировки учётных записей. |
| Server 2025 | Единственная имеющаяся сейчас машина. Проверено: OpenSSH ставится как компонент, оболочка sshd переключается на PowerShell, NLA и TLS включаются, `AllowAdministratorLockout` доступен. |

## Предусловия для каждой машины

Общие:

- машина развёрнута тем же `infra/windows/setup-windows-target.ps1`, что и
  боевой узел; ручные донастройки не допускаются, любая необходимость ручного
  шага — самостоятельный дефект автоматизации;
- прогон `scripts/qa/check-target.ps1` выполнен и приложен к журналу: если
  приёмка узла не пройдена, результаты сценариев не интерпретируемы;
- созданы две учётные записи сотрудников, например `qa_a` и `qa_b`, обе в группе
  `Remote Desktop Users`, пароли известны проверяющему;
- на цели установлены раскладки клавиатуры: английская и русская;
- часовой пояс и время синхронизированы: расхождение искажает сопоставление
  журналов;
- зафиксированы версия ОС и номер сборки (`Get-CimInstance Win32_OperatingSystem`),
  версия платформы и коммит.

Для сценариев с браузером: узел платформы развёрнут и доступен по HTTPS.
Обычный HTTP не годится — часть проверок буфера обмена в браузере невозможна
вне защищённого контекста, и результат будет не про платформу, а про ограничение
браузера.

Для сценариев с двумя пользователями на серверных ОС: заранее решить и записать,
проверяется ли машина с ролью RD Session Host или без неё. Ожидаемый результат
для этих двух случаев разный.

Инструменты сбора доказательств на цели:

```powershell
qwinsta                                     # список сеансов и их состояние
Get-WinEvent -LogName 'Microsoft-Windows-TerminalServices-LocalSessionManager/Operational' -MaxEvents 50
Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4624, 4625, 4634, 4647 } -MaxEvents 50
Get-WinEvent -LogName 'OpenSSH/Operational' -MaxEvents 50
```

## Сценарий 1. RDP через браузер

**Предусловия.** Узел платформы доступен по HTTPS; учётная запись `qa_a` может
входить по RDP; на цели включены русская и английская раскладки; нативный клиент
`mstsc` с той же машины проверяющего работает — это контрольный опыт.

### 1.1 Подключение

Шаги: открыть в браузере страницу цели, ввести учётные данные `qa_a`, дождаться
рабочего стола. Повторить в двух браузерах на движках Chromium и Firefox.

Ожидаемо: рабочий стол появляется, сеанс в `qwinsta` в состоянии `Active`,
в журнале LocalSessionManager есть событие входа с адресом клиента.

Дефект или ограничение: если не подключается ни через браузер, ни через `mstsc` —
смотреть NLA, `fDenyTSConnections`, членство в `Remote Desktop Users`, правила
брандмауэра; это настройка узла, а не платформы. Если `mstsc` работает, а
браузер нет — дефект платформы.

### 1.2 Ввод с клавиатуры и мыши

Шаги: набрать в «Блокноте» строку из латиницы, цифр и знаков `@ # $ ^ & * ( ) _ - = + [ ] { } ; ' " \ | / ? ~`; проверить сочетания Shift, Ctrl+C, Ctrl+V, Alt+Tab, стрелки, Home/End, Backspace/Delete; кликнуть левой, правой и средней кнопкой, проверить двойной клик, перетаскивание и колесо прокрутки.

Ожидаемо: символы совпадают с набранными, сочетания работают, дублирования и
залипания клавиш нет, координаты курсора соответствуют месту клика.

Дефект или ограничение: Ctrl+Alt+Del в браузер не передаётся принципиально, это
защищённая последовательность — `limit`, но платформа обязана предоставить
эквивалент (экранная кнопка). Перехват браузером своих сочетаний (Ctrl+W,
Ctrl+T, F5, F11) — ограничение браузера; ожидается, что платформа предупреждает
об этом или предлагает захват клавиатуры. Смещение курсора относительно клика —
дефект платформы, но перед этим проверить масштабирование дисплея на машине
проверяющего: при масштабе, отличном от 100 %, ошибки координат бывают вызваны
отсутствием DPI-осведомлённости, см. `docs/design/environments.md`.

### 1.3 Раскладка и русские символы

Шаги: переключить раскладку на русскую средствами гостевой ОС, набрать
`Проверка ввода, ёжик, «кавычки», тире — и Ё`; затем переключить раскладку
средствами локальной ОС и повторить; проверить ввод в «Блокнот», в PowerShell и
в поле поиска меню «Пуск».

Ожидаемо: текст совпадает посимвольно, включая `ё`, `Ё`, `«»` и тире.

Дефект или ограничение: если русской раскладки нет в гостевой системе — это
предусловие не выполнено, а не дефект. Если раскладка есть, `mstsc` вводит
русский текст верно, а через браузер получается латиница, мусор или пропуск
символов — дефект платформы (типичная причина — передача кодов клавиш вместо
символов). Расхождение из-за того, что раскладки локальной и гостевой систем
переключаются независимо, — известное свойство RDP: состояние раскладки
принадлежит гостевой системе. Это `limit`, но ожидается, что платформа
показывает текущую раскладку сеанса.

### 1.4 Изменение разрешения

Шаги: изменить размер окна браузера и перейти в полноэкранный режим; на
подключённом сеансе изменить разрешение в параметрах гостевой системы;
переподключиться и проверить, сохранилось ли разрешение.

Ожидаемо: изображение подстраивается без обрыва сеанса, содержимое не обрезано,
пропорции сохранены.

Дефект или ограничение: динамическое изменение разрешения требует поддержки в
стеке RDP гостевой системы. На Server 2016 оно может отсутствовать — проверить
контрольным опытом: если `mstsc` при растягивании окна тоже не меняет разрешение
динамически, это `limit` для этой ОС. На Windows 11 и Server 2022/2025
отсутствие динамического изменения — дефект платформы. Появление чёрных полей
вместо масштабирования допустимо, если это заявленный режим отображения;
обрезание части рабочего стола без возможности прокрутки — дефект.

## Сценарий 2. SSH

**Предусловия.** OpenSSH Server установлен и запущен; ключ проверяющего
добавлен: для членов группы Administrators — в
`C:\ProgramData\ssh\administrators_authorized_keys`, для обычных учётных
записей — в `%USERPROFILE%\.ssh\authorized_keys`; вход по паролю отключён.

### 2.1 Вход по ключу и отказ по паролю

Шаги:

```powershell
ssh -o BatchMode=yes <user>@<host> "hostname"
ssh -o BatchMode=yes -o PubkeyAuthentication=no -o PreferredAuthentications=password `
    -o ConnectTimeout=10 <user>@<host> hostname
```

Ожидаемо: первая команда возвращает имя машины и код 0; вторая — отказ
`Permission denied (publickey).` и код 255. Успешный вход по паролю здесь —
серьёзный дефект, а не удобство.

Дефект или ограничение: молчаливый отказ по ключу у члена группы Administrators
почти всегда означает права на файл ключей или расположение файла: sshd
отказывает без объяснений, если файл доступен кому-то кроме Administrators и
SYSTEM, и игнорирует `authorized_keys` в профиле администратора. Это настройка
узла (`limit` для платформы, но дефект автоматизации, если скрипт заявляет её
выполненной). Проверяется пунктами SSH-09 и SSH-10 из `check-target.ps1`.

### 2.2 Интерактивная оболочка

Шаги: подключиться без команды, проверить `$PSVersionTable`, вывод `Get-ChildItem`,
переход по каталогам, `Ctrl+C` на длительной команде, историю по стрелке вверх,
вывод русского текста и путей с кириллицей.

Ожидаемо: приглашение PowerShell, а не `cmd`; `Ctrl+C` прерывает команду, не
разрывая сеанс; русский текст читается.

Дефект или ограничение: `cmd.exe` вместо PowerShell — дефект настройки узла
(`DefaultShell`). Мусор вместо кириллицы в интерактивной оболочке при верной
кодировке на стороне клиента — ограничение консоли Windows PowerShell 5.1,
обходится установкой `[Console]::OutputEncoding`; отмечать как `limit` с
указанием обхода, но если платформа сама читает вывод и портит кодировку — это
дефект платформы.

### 2.3 Длинный вывод

Шаги:

```powershell
ssh <user>@<host> "1..200000 | ForEach-Object { 'строка ' + `$_ }" | Measure-Object -Line
```

Ожидаемо: получено ровно 200000 строк, порядок сохранён, обрывов и зависаний
нет; поток не блокируется на середине.

Дефект или ограничение: усечение вывода, зависание или переупорядочивание —
дефект платформы. Замедление на очень широких строках может быть свойством
терминала; фиксировать с числами.

### 2.4 Обрыв связи

Шаги: во время активного сеанса разорвать сеть на стороне клиента (отключить
интерфейс или заблокировать порт), подождать больше, чем
`ServerAliveInterval × ServerAliveCountMax`; затем восстановить сеть и
подключиться заново. На цели проверить `qwinsta` и наличие осиротевших процессов
`sshd` и `powershell`.

Ожидаемо: клиент сообщает о потере связи, а не висит бесконечно; на цели сеанс
и его процессы закрываются; повторное подключение проходит; лимит
`MaxAuthTries` не мешает.

Дефект или ограничение: накопление процессов `powershell` от прерванных сеансов
— дефект. Бесконечное ожидание у клиента без keepalive — не дефект платформы, а
поведение SSH по умолчанию: проверять с явно заданными `ServerAliveInterval` и
`ServerAliveCountMax`.

## Сценарий 3. VNC

**Предусловия.** Зафиксировать, как запущен VNC-сервер: как служба от SYSTEM или
как приложение в сеансе пользователя. От этого зависит весь ожидаемый результат,
и без этой записи сценарий не интерпретируем.

### 3.1 Подключение

Шаги: подключиться штатным VNC-клиентом, затем через платформу; сравнить
изображение, задержку и реакцию на ввод.

Ожидаемо: виден текущий рабочий стол, ввод доходит, изображение обновляется.

### 3.2 Экран блокировки

Шаги: заблокировать сеанс (`Win+L`) и подключиться заново; отдельно проверить
поведение при появлении запроса UAC.

Ожидаемо: VNC-сервер, работающий как служба от SYSTEM и имеющий право
захватывать защищённый рабочий стол, показывает экран блокировки и запрос UAC.

Дефект или ограничение: VNC-сервер, запущенный как обычное приложение в сеансе
пользователя, экран блокировки и запрос UAC показать не может — это изоляция
защищённого рабочего стола в Windows, `limit`. Отличать по тому, как запущен
сервер: чёрный экран вместо экрана блокировки у пользовательского процесса —
ожидаемо, у службы от SYSTEM — дефект.

### 3.3 Отсутствие активного сеанса

Шаги: завершить все интерактивные сеансы (`logoff` для всех, проверить
`qwinsta`), затем подключиться по VNC.

Ожидаемо: у службы от SYSTEM — экран входа в систему; у пользовательского
процесса — подключение невозможно, потому что захватывать нечего.

Дефект или ограничение: невозможность подключиться к машине без активного
сеанса при пользовательском режиме запуска — `limit`. Дефект платформы —
отсутствие внятного сообщения: пользователь должен понимать, что нужно сначала
войти по RDP или что VNC-сервер должен работать как служба. Отдельно проверить
взаимодействие с RDP: подключение по RDP переводит консольный сеанс в
отключённое состояние, поэтому VNC, привязанный к консоли, покажет экран
блокировки. Это ожидаемо и должно быть описано в документации, а не считаться
дефектом.

## Сценарий 4. Передача файлов в обе стороны

**Предусловия.** Подготовить набор файлов и записать их контрольные суммы:

```powershell
$dir = 'C:\qa-transfer'
New-Item -ItemType Directory -Force -Path $dir | Out-Null
'содержимое' | Set-Content "$dir\простой.txt" -Encoding UTF8
'содержимое' | Set-Content "$dir\Отчёт за август — копия (1).txt" -Encoding UTF8
'содержимое' | Set-Content "$dir\файл с пробелами и ёЁ.txt" -Encoding UTF8
# файл больше 100 МБ, заполненный случайными данными: сжимаемый нуль-файл
# скрыл бы ограничения по объёму
$fs = [System.IO.File]::Create("$dir\big-150mb.bin")
$buf = New-Object byte[] (1MB)
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
1..150 | ForEach-Object { $rng.GetBytes($buf); $fs.Write($buf, 0, $buf.Length) }
$fs.Close()
Get-ChildItem $dir | Get-FileHash -Algorithm SHA256 | Format-List Path, Hash
```

### 4.1 Передача на цель

Шаги: передать каждый файл через платформу; на цели сверить SHA256 и имя
посимвольно:

```powershell
Get-ChildItem 'C:\qa-received' | ForEach-Object {
    '{0} | {1} | {2}' -f $_.Name, $_.Length, (Get-FileHash $_.FullName -Algorithm SHA256).Hash
}
# посимвольное сравнение имени: похожие символы и разные формы Unicode
[int[]][char[]]'Отчёт за август — копия (1).txt'
```

Ожидаемо: SHA256 совпадает, размер совпадает, имя совпадает посимвольно,
включая `ё` и длинное тире.

### 4.2 Передача с цели

Шаги: те же файлы забрать обратно на машину проверяющего и снова сверить хеши и
имена.

Ожидаемо: то же. Отдельно проверить, что файл, созданный на цели с кириллическим
именем, доходит без искажений: направление «с цели» чаще ломает кодировку, потому
что имя формирует Windows.

### 4.3 Файл больше 100 МБ

Шаги: передать `big-150mb.bin` в обе стороны, замерить время, наблюдать
индикатор прогресса; повторить с обрывом сети посередине.

Ожидаемо: файл доходит целиком, хеш совпадает, прогресс отображается,
таймаутов нет; при обрыве платформа сообщает об ошибке и не оставляет
повреждённый файл, выданный за целый.

Дефект или ограничение: порог именно на 100 МБ выбран не случайно — типовые
рубежи перед приложением (обратный прокси, туннель Cloudflare) по умолчанию
ограничивают размер тела запроса, и отказ на файле в 150 МБ при успешной
передаче 90 МБ означает ограничение инфраструктуры, а не приложения. Проверять
контрольным опытом: та же передача в обход туннеля, напрямую. Если напрямую
проходит, а через туннель нет, это дефект конфигурации инфраструктуры, и его
нужно вести отдельно от дефектов платформы.

Отличать также:

- имена с символами, недопустимыми в Windows (`: * ? " < > |`), создать нельзя —
  `limit`, а не дефект;
- путь длиннее 260 символов без включённой поддержки длинных путей — `limit`
  Windows, но платформа обязана сообщить об ошибке внятно, а не молча потерять
  файл;
- различие форм Unicode в именах (`ё` как один символ или как `е` с
  диакритикой): имя визуально совпадает, а посимвольно нет. Это дефект
  нормализации на стороне платформы, и находится он только сравнением кодов
  символов, поэтому шаг с `[int[]][char[]]` обязателен;
- скорость: замерить и записать. Явно низкая скорость не дефект по этому
  чек-листу, но фиксируется как наблюдение.

## Сценарий 5. Буфер обмена в обе стороны

**Предусловия.** Страница платформы открыта по HTTPS: в незащищённом контексте
браузер не даёт доступ к буферу обмена, и результат будет не о платформе.

### 5.1 С машины проверяющего на цель

Шаги: скопировать локально и вставить в «Блокнот» на цели: короткую строку
латиницей; строку `Проверка, ёжик, «кавычки», тире —`; многострочный текст из
пяти строк, включая пустую строку в середине; текст с табуляциями; текст около
1 МБ.

Ожидаемо: вставленное совпадает с исходным, переводы строк сохранены, пустая
строка не потеряна, табуляции не заменены пробелами.

### 5.2 С цели на машину проверяющего

Шаги: то же в обратном направлении, включая копирование вывода PowerShell с
кириллицей и путей вида `C:\Пользователи\qa_a\Документы`.

Ожидаемо: то же.

Дефект или ограничение: перевод строки в Windows — `CRLF`; получение `LF`
вместо `CRLF` при вставке в «Блокнот» современных сборок Windows отображается
корректно, но при вставке в старые редакторы даёт одну строку. Фиксировать
фактические байты, а не вид на экране. Требование жеста пользователя для доступа
к буферу и разрешение в браузере — ограничение браузера (`limit`), но
отсутствие подсказки об этом — дефект удобства платформы. Копирование
изображений и форматированного текста: если платформа поддерживает только
обычный текст, это ограничение реализации; отмечать как дефект только если
поддержка заявлена. Обрезание текста около 1 МБ — дефект платформы, если
ограничение не задокументировано.

## Сценарий 6. Одновременные сеансы двух пользователей

Ожидаемый результат принципиально зависит от типа системы, см. раздел о числе
сеансов. Перед прогоном записать: тип ОС, установлена ли роль RD Session Host,
значение `LicensingType`.

### 6.1 Клиентские Windows 10 и 11

Шаги: войти как `qa_a` через платформу, начать что-то делать (открыть «Блокнот»
с текстом); из другого браузера или с другой машины войти как `qa_b`;
зафиксировать, что видит `qa_a` и что видит `qa_b`; проверить `qwinsta`.

Ожидаемо: сеанс `qa_a` завершается или переходит в отключённое состояние,
работать одновременно они не могут. `qa_b` получает свой рабочий стол.
В `qwinsta` активен один интерактивный сеанс.

Как отличить дефект от ограничения: само вытеснение — `limit`, свойство
клиентской Windows. Дефектами являются: отсутствие у `qa_a` какого-либо
сообщения о причине обрыва; интерфейс платформы, показывающий сеанс `qa_a`
активным после вытеснения; чёрный экран или зависание вместо корректного
завершения; несохранённые данные, потерянные без предупреждения там, где
Windows штатно предупреждает; и, самое серьёзное, если `qa_b` видит рабочий стол
или содержимое сеанса `qa_a` — это нарушение изоляции и блокирующий дефект.

### 6.2 Серверные ОС без роли RD Session Host

Шаги: подключиться двумя административными учётными записями, затем третьей.

Ожидаемо: два сеанса работают параллельно и независимо; третье подключение
отклоняется с сообщением о превышении числа допустимых подключений.

Как отличить: отказ третьему — `limit` режима удалённого администрирования.
Дефект — если платформа показывает отказ как внутреннюю ошибку, не объясняя
причину, или если вместо отказа вытесняет один из работающих сеансов.

### 6.3 Серверные ОС с ролью RD Session Host

Шаги: подключиться двумя обычными учётными записями `qa_a` и `qa_b`
одновременно, работать параллельно не менее десяти минут; проверить изоляцию:
рабочие столы, буфер обмена, переменные окружения, папки профилей, список
процессов, а также данные платформы — закладки, сохранённые сессии,
учётные данные.

Ожидаемо: сеансы полностью независимы; `qa_a` не видит файлов, буфера обмена и
сохранённых данных `qa_b`; в `qwinsta` два активных сеанса с разными
идентификаторами.

Как отличить: любое пересечение данных — блокирующий дефект платформы, а не
ограничение ОС. Отказ подключения после истечения 120-дневного льготного периода
без сервера лицензий — `limit` лицензирования RDS, и в отчёте это нужно
указывать вместе с датой начала периода.

### 6.4 Отзыв доступа закрывает активные сеансы

Шаги: при активном сеансе `qa_b` отозвать у него доступ средствами платформы;
не переподключаясь, попробовать продолжить работу в открытом сеансе; затем
попробовать войти заново.

Ожидаемо: активный сеанс прерывается, а не только запрещается новый вход.

Как отличить: сохранение работоспособности активного сеанса после отзыва — дефект
платформы, а не свойство Windows: закрыть сеанс можно принудительно. Это
отдельная проверка из брифа, и она важнее, чем запрет нового входа.

## Что блокирует прогон сейчас

1. **Нет машин, кроме Server 2025.** Windows 10, Windows 11, Server 2016, 2019 и
   2022 отсутствуют. Это блокирует все строки матрицы в пяти столбцах из шести,
   включая единственные проверки вытеснения сеанса на клиентских ОС — на
   серверной системе они невоспроизводимы в принципе.
2. **Узел платформы не развёрнут.** Продуктовый код не установлен, узел с
   веб-интерфейсом отсутствует, домена и Cloudflare нет. Это блокирует все
   сценарии, идущие через браузер: RDP в браузере, буфер обмена, передачу файлов
   через интерфейс платформы и отзыв доступа.
3. **VNC не установлен** ни на одной машине, режим запуска не выбран. Блокирует
   весь сценарий 3. До прогона нужно решить, работает VNC-сервер как служба от
   SYSTEM или как пользовательский процесс: без этого решения ожидаемый результат
   не определён.
4. **Роль RD Session Host не установлена** на Server 2025, `LicensingType=1`.
   Многопользовательские сценарии проверяемы только в варианте 6.2, то есть в
   пределах двух административных сеансов. Установка роли требует перезагрузки и
   запускает 120-дневный льготный период — решение владельца.
5. **Учётных записей сотрудников нет:** группа `Remote Desktop Users` на
   Server 2025 пуста, включена одна учётная запись `root`. Проверки с двумя
   пользователями и проверки изоляции требуют `qa_a` и `qa_b`.
6. **Не проверен подъём после перезагрузки** (пункт OS-04 отчёта приёмки).
   Формально это не блокирует сценарии, но пока регресс не выполнен, любой сбой
   после рестарта нельзя будет отличить от давно существовавшего дефекта
   автоматизации.

Что можно прогнать на имеющейся машине без дополнительных развёртываний:
сценарий 2 полностью (SSH), включая длинный вывод и обрыв связи, и сценарий 4
в варианте передачи по `scp`/`sftp` как базовую линию для сравнения с передачей
через платформу. Передача файлов по `scp` на Server 2025 с оболочкой PowerShell
уже подтверждена работоспособной в ходе приёмки.

# Граница доверия на уровне Windows

## Проблема, из которой всё следует

В Windows два процесса одного пользователя — это один субъект безопасности.
Пользователь может открыть свой процесс с правом `PROCESS_ALL_ACCESS`, записать
в его память, создать в нём поток, подменить файл на диске перед запуском,
переписать ключ автозапуска, изменить задание планировщика. Никакой код внутри
процесса от этого не защищает.

Отсюда простой вывод: разделение на «модуль политики» и «модуль исполнения»
внутри одного процесса или между двумя процессами одного пользователя не
является границей безопасности. Это разделение ответственности в исходниках,
полезное для чтения кода и бесполезное против нарушителя.

Ровно эта ошибка заложена в исходной системе: агент, сессии, учётные данные всех
сотрудников и проверки прав живут в одном процессе Node от имени одного
пользователя. Ограничение агента там технически невыразимо — ограничивать нечего
и нечем.

Поэтому граница проводится по учётным записям ОС, а не по модулям.

## Субъекты

Четыре учётные записи, ни одна из них не входит в администраторы.

| Учётная запись | Роль | Запись разрешена | Ключевое ограничение |
|---|---|---|---|
| `svc_af_policy` | политика и реестры | политика, конфигурация | не выполняет инструменты |
| `svc_af_audit` | журнал аудита | хранилище журнала | принимает события только по локальному каналу |
| `svc_af_broker` | брокер учётных данных | хранилище секретов | не отдаёт секрет наружу, только открывает соединение |
| `svc_af_exec` | исполнитель инструментов | рабочий и карантинный корни | не может писать в политику, журнал, конфигурацию и секреты |

Минимум релиза A: политика, аудит и брокер отделены от исполнителя. Разнесение
этих трёх между собой желательно и относится к релизу B — оно уменьшает
последствия ошибки в самой плоскости управления, но не закрывает главный путь
атаки, а главный путь идёт через исполнителя.

Пятая запись, `svc_af_desktop`, появляется только вместе с автоматизацией
рабочего стола, и о ней отдельный раздел ниже.

## Что снято у исполнителя

Привилегии перечислены не для полноты, а потому что каждая из них обходит
ограничения, на которых держится вся остальная конструкция.

| Привилегия | Что даёт нарушителю |
|---|---|
| `SeDebugPrivilege` | открыть любой процесс, включая брокер секретов, и прочитать его память |
| `SeBackupPrivilege` | читать файлы в обход списков доступа — то есть журнал и хранилище секретов |
| `SeRestorePrivilege` | писать файлы в обход списков доступа, включая политику |
| `SeTakeOwnershipPrivilege` | стать владельцем объекта и переписать его список доступа |
| `SeImpersonatePrivilege` | классический путь повышения прав через именованный канал |
| `SeAssignPrimaryTokenPrivilege` | запустить процесс с чужим маркером доступа |
| `SeLoadDriverPrivilege` | код в ядре, после чего обсуждать остальное бессмысленно |
| `SeSecurityPrivilege` | правка политики аудита самой Windows |
| `SeCreateSymbolicLinkPrivilege` | создать ссылку, выводящую за пределы разрешённого корня |

Остаётся `SeChangeNotifyPrivilege` — без неё не работает обход каталогов.

Дополнительно исполнитель запускается в объекте задания с пределами по памяти,
числу процессов и времени, с запретом создания процессов вне задания и с
ограничениями пользовательского интерфейса: без доступа к буферу обмена, к чужим
рабочим столам и к оконным сообщениям других станций.

## Что исполнителю запрещено писать

Список доступа настраивается так, чтобы у `svc_af_exec` не было права записи ни в
одну из этих областей, и права чтения — только там, где оно действительно нужно:

- файлы политики и реестр целей: чтение через службу политики, прямого доступа к
  файлам нет;
- хранилище журнала аудита: доступа нет вовсе, события уходят через локальный
  канал службе аудита;
- хранилище учётных данных: доступа нет, соединения открывает брокер;
- каталог приложения, его зависимости и конфигурация службы;
- ключи автозапуска, задания планировщика, каталоги автозагрузки;
- `%WINDIR%`, `%ProgramFiles%`, корень системного диска;
- профили пользователей целиком, включая `.ssh`, профили браузеров, хранилища
  паролей и файлы `known_hosts`.

Отдельным пунктом: исполнитель не может изменить условия собственного запуска.
Если он может переписать службу, задание планировщика или свой исполняемый файл,
то все ограничения выше действуют до первого перезапуска, то есть не действуют.

Проверять это чтением кода бессмысленно, поэтому проверка вынесена в приёмку:
попытка записи в каждую из перечисленных областей от имени `svc_af_exec` должна
завершаться отказом ОС, а не отказом приложения. Разница существенная: отказ
приложения означает, что путь закрыт одной проверкой в одном месте.

## Журнал пишется не в файл

Исполнитель не держит дескриптора на хранилище журнала. Он отправляет события по
именованному каналу службе аудита, которая работает от `svc_af_audit` и является
единственным владельцем хранилища.

Причина простая: «журнал только на дозапись» на уровне списков доступа Windows
выражается плохо, а полностью не выражается никак — обладатель права записи в
файл почти всегда может его усечь или переименовать. Отсутствие дескриптора —
единственная надёжная форма «не может испортить».

Служба аудита ведёт цепочку хешей и периодически выкладывает подписанную
контрольную точку во внешнее хранилище. Формула цепочки и правила редактирования
— в [agent-control-plane.md](agent-control-plane.md).

## Секреты не проходят через исполнителя

Брокер (`svc_af_broker`) владеет хранилищем учётных данных, сам устанавливает
соединение с целью и передаёт исполнителю уже открытый дескриптор — на уровне ОС
это унаследованный дескриптор сокета либо соединение, проксируемое брокером.
Пароль, закрытый ключ и токен не появляются ни в памяти исполнителя, ни в его
аргументах, ни в переменных окружения.

Переменные окружения упомянуты отдельно, потому что это распространённый способ
передать секрет дочернему процессу, и он плох: переменные окружения процесса
читаются любым, кто может открыть процесс, попадают в дампы памяти и в отчёты о
сбоях.

## Автоматизация рабочего стола

Обычная автоматизация интерфейса — нажатия, ввод текста, чтение содержимого окон
— на Windows не изолируется. Процесс, имеющий доступ к рабочему столу, имеет
доступ ко всему, что на этом рабочем столе: к окнам чужих приложений, к буферу
обмена, к содержимому экрана, к оконным сообщениям. Границы между приложениями на
одном рабочем столе нет.

Поэтому:

1. Такая автоматизация выполняется отдельной учётной записью `svc_af_desktop` на
   отдельной сессии и отдельном рабочем столе, а не на рабочем столе сотрудника.
2. Любое действие помечается риском не ниже `high` и выполняется под
   наблюдением. В релизе B оно не переходит в автономный режим вместе с
   остальными: для него требуется отдельное решение.
3. На этом рабочем столе не выполняется вход в почту, банк-клиенты и системы
   управления инфраструктурой. Всё, что там открыто, следует считать доступным
   агенту.
4. Учётная запись рабочего стола не имеет доступа к хранилищу учётных данных.
   Если сценарию нужен вход в приложение, вход выполняет брокер, а не агент,
   печатающий пароль в поле ввода.

Честная оговорка: пункт 3 — организационное ограничение, а не техническое. Его
нельзя обеспечить настройкой, и это остаточный риск, записанный в модели угроз.

## Многоузловой режим

Когда узлов становится несколько, добавляется личность устройства: сопряжение по
одноразовому коду, ключ в TPM, сертификат от внутреннего центра сертификации,
mTLS между узлами. Токен агента привязывается к отпечатку сертификата через
`cnf`, поэтому украденный на одном узле токен не работает на другом.

Ограничение области: узел получает полномочия только на свои цели. Компрометация
одного узла не должна давать доступ ко всем — это выражается тем, что полномочия
выдаются с селектором машин, а не с признаком «узел доверенный».

Подробности транспорта и сопряжения — в
[agent-mcp-transport.md](agent-mcp-transport.md).

## Как это проверяется

Проверки для приёмки, в порядке от простого к сложному:

1. `whoami /priv` от имени каждой служебной записи: список привилегий совпадает с
   объявленным в записи субъекта.
2. Попытка записи в каждую защищённую область от имени `svc_af_exec`: отказ ОС.
3. Попытка открыть процесс брокера от имени `svc_af_exec`: отказ.
4. Попытка изменить конфигурацию службы исполнителя и его задание в планировщике:
   отказ.
5. Остановка службы аудита: исполнитель обязан прекратить выполнение
   инструментов, а не продолжить без журнала.
6. Перезапуск узла: все ограничения восстанавливаются автоматически, без ручных
   действий.

Пункт 5 стоит отдельно. Работа без журнала — это работа без возможности
разобраться в последствиях, и она должна быть отказом, а не деградацией.

Полная матрица — в [agent-threat-model.md](agent-threat-model.md).

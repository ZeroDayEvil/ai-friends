# Размещение панели на сервере с ISPmanager 6

Комплект для сервера, который нам не принадлежит и на котором уже работают
десятки клиентских сайтов. Отличие от остального `infra/vps/` — здесь ничего не
устанавливается и не настраивается «под нас»: мы вписываемся в чужую
конфигурацию с минимальным следом.

**`infra/vps/setup-server.sh` на таком сервере запускать нельзя.** Он рассчитан
на чистую Ubuntu и сбрасывает фаервол, из-за чего закрываются порты 80, 443 и
1500: клиентские сайты останавливаются, панель ISPmanager становится
недоступна. Подробно — в [SAFETY.md](SAFETY.md), раздел 0.

## Состав

| Файл | Назначение |
|---|---|
| [`inventory.sh`](inventory.sh) | инвентаризация сервера, только чтение, ни один файл не меняется |
| [`deploy-panel.sh`](deploy-panel.sh) | развёртывание панели, идемпотентно, с `--dry-run` и резервными копиями |
| [`nginx-panel.conf.sample`](nginx-panel.conf.sample) | фрагмент проксирования для nginx с подстановками |
| [`apache-panel.conf.sample`](apache-panel.conf.sample) | то же для Apache без nginx |
| [`reverse-proxy.md`](reverse-proxy.md) | как подключить домен к `127.0.0.1:5577`, чтобы панель не затёрла настройку |
| [`rollback.md`](rollback.md) | откат по каждому шагу, за минуту |
| [`SAFETY.md`](SAFETY.md) | контрольный список, классификация шагов по риску, порядок действий |

## Порядок

```bash
sudo ./inventory.sh > inventory.txt          # 1. узнать факты
sudo ./deploy-panel.sh --dry-run             # 2. прочитать план
sudo ./deploy-panel.sh                       # 3. поднять приложение на loopback
sudo ./deploy-panel.sh --with-proxy nginx    # 4. установить фрагмент, без reload
nginx -t && systemctl reload nginx           # 5. применить
```

Подробности и обоснование каждого шага — в [SAFETY.md](SAFETY.md), раздел 4. Без
шага 1 остальные не начинать: способ проксирования зависит от того, что
покажет отчёт.

## Целевая схема

Приложение слушает только `127.0.0.1:5577`. Наружу его отдаёт уже работающий
веб-сервер сервера через `mql5.ink` на подпути `/panel/`. Порты 80 и 443
остаются за веб-сервером панели, новые порты не открываются.

Это временное решение. Постоянное — `cloudflared` на целевом домене в зоне
Cloudflare: исходящее соединение, вход через Zero Trust Access, ни одного
открытого порта и ни одной правки в конфигурации чужого веб-сервера. К
`mql5.ink` туннель не применим: домен обслуживается напрямую, а не через
Cloudflare (см. `docs/design/dns-cloudflare-setup.md`).

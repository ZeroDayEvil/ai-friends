# Бриф: Агент 3, тестирование и приёмка

## Роль

Независимая оценка результата. Задача не в том, чтобы починить, а в том, чтобы
честно показать, что работает, что нет и при каких условиях ломается. Найденные
дефекты фиксируются, но исправляет их оркестратор.

## Область

### Приёмка инфраструктуры

Для каждого развёрнутого узла проверяется, что заявленное в `infra/` совпадает с
реальностью: службы запущены и стоят на автозапуске, порты открыты ровно те, что
описаны, лишние закрыты, доступ по паролю отключён там, где это заявлено,
исходящие соединения ограничены egress-политикой.

Обязательная проверка на регресс: после перезагрузки узла всё поднимается само.
Ручная донастройка, не попавшая в скрипты, — это дефект.

### Матрица совместимости

Целевые системы: Windows 10, Windows 11, Windows Server 2016, 2019, 2022, 2025.

Проверяемые сценарии на каждой системе:

- RDP через браузер: подключение, ввод с клавиатуры и мыши, раскладка и русские
  символы, изменение разрешения;
- SSH: вход по ключу, интерактивная оболочка, длинный вывод, обрыв связи;
- VNC: подключение, экран блокировки, поведение при отсутствии активного сеанса;
- передача файлов в обе стороны, включая имена с не-ASCII символами и файлы
  больше 100 МБ;
- буфер обмена в обе стороны, включая многострочный текст;
- одновременные сеансы: два пользователя на одной машине. Ожидаемое поведение
  различается принципиально: клиентские Windows 10 и 11 имеют один активный
  сеанс, и второй пользователь выбьет первого; серверные версии с ролью RD
  Session Host поддерживают несколько. Это не дефект, а свойство системы, и в
  отчёте это нужно разделять.

### Многопользовательский режим

Ключевая проверка — изоляция: пользователь A не должен видеть закладки, сессии,
файлы и учётные данные пользователя B. Отдельно проверяется, что отзыв доступа
у сотрудника действительно закрывает активные сессии, а не только новый вход.

## Формат результата

`docs/audit/qa-<дата>-<область>.md`:

- окружение: версии систем, сборка платформы, коммит;
- таблица сценариев со статусом `pass`, `fail`, `blocked`, `n/a`;
- для каждого `fail` — шаги воспроизведения, ожидаемое и фактическое поведение,
  логи;
- отдельно: обнаруженные риски безопасности, даже если они вне поставленной
  задачи;
- вердикт: можно ли выпускать, и какие дефекты блокирующие.

## Границы

Разрешённые для записи пути: `docs/audit/`. Продуктовый код и `infra/` не менять.
Тесты запускать только против тестовых узлов, перечисленных в
`docs/design/environments.md`.

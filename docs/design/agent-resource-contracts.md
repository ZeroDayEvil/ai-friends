# Контракты доступа к ресурсам

## Файлы: удержание по дескриптору

### Почему проверка пути не работает

Проверка «путь начинается с разрешённого каталога» ломается по двум независимым
причинам.

Первая — состязание. Между проверкой строки и открытием файла проходит время, и
за это время каталог на пути можно заменить точкой соединения. Проверка получила
один объект, открытие — другой. На Windows это не редкий случай: создание точки
соединения не требует прав администратора.

Вторая — количество написаний одного и того же места. Символические ссылки,
точки соединения, точки монтирования томов, короткие имена в формате 8.3, `\\?\`,
`\\.\`, `\\?\GLOBALROOT`, UNC-пути, диск-относительные пути вида `C:каталог`,
завершающие точки и пробелы, регистр, разные формы нормализации Unicode,
альтернативные потоки данных. Список запрещённых написаний по определению не
содержит того, о чём автор не подумал.

### Как делается вместо этого

1. **Корень — объект реестра.** Он разрешается один раз при запуске службы в
   канонический путь и в пару «серийный номер тома плюс 128-битный
   идентификатор файла». Удержание проверяется по идентификатору объекта, а не
   по строке.
2. **Открытие покомпонентно, без разыменования точек повторного разбора.**
   Каждый компонент пути открывается относительно уже открытого дескриптора
   родителя. Точка повторного разбора внутри корня в релизе A — отказ, а не
   переход.
3. **Проверка после открытия, работа с дескриптором.** У полученного дескриптора
   запрашивается канонический путь и идентификатор файла; они сверяются с
   корнем. Дальше все операции идут через этот дескриптор. Повторное открытие по
   строке пути запрещено — именно оно возвращает состязание, которое мы только
   что закрыли.
4. **Аргумент — пара, а не строка.** В проводном формате путь выражается как
   `{root_id, relpath}`, см. `security/schemas/common.v1.json`. Это даёт три
   вещи сразу: невозможность прислать абсолютный путь, устойчивый хеш аргументов
   для одобрения и осмысленный селектор в полномочии.

### Что отвергается на уровне схемы

Схема `relpath` не принимает: абсолютные пути, обратную косую черту, двоеточие
(и вместе с ним альтернативные потоки данных), символы `* ? " < > |`, управляющие
символы, `.` и `..` как компоненты, завершающие точки и пробелы, зарезервированные
имена устройств `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, в том
числе с расширением.

Это первый рубеж, а не единственный. Он ценен тем, что срабатывает до того, как
строка дойдёт до кода открытия файла, и тем, что его нарушение видно в примере
`security/schemas/examples/tool-request.path-traversal.invalid.json`.

Дополнительно на стороне исполнителя:

- строки приводятся к NFC до сравнения; сравнение регистронезависимое, хранение —
  с сохранением написания;
- имя, похожее на короткую форму 8.3, не принимается; после открытия
  канонический путь сверяется с намерением вызывающего;
- на запись файл открывается с созданием нового объекта; существующая
  символическая ссылка не разыменовывается;
- в строгом режиме файл с числом жёстких ссылок больше единицы не отдаётся:
  жёсткая ссылка внутри корня может указывать на файл снаружи, и для отдачи
  наружу это тот же файл.

### Защищённые области

Эти области недоступны инструментам ни на чтение, ни на запись, независимо от
выданных полномочий, и запрет продублирован списками доступа ОС:

- хранилище журнала аудита, хранилище учётных данных, файлы политики и реестров;
- каталог приложения, его зависимости, конфигурация служб;
- ключи автозапуска, задания планировщика, каталоги автозагрузки;
- `%WINDIR%`, `%ProgramFiles%`, корень системного диска;
- профили пользователей: `.ssh`, `known_hosts`, профили браузеров, хранилища
  паролей, файлы почтовых клиентов.

Отказ по этим областям имеет собственный код `protected_path`, отличный от
`containment_violation`. Разница нужна в разборе: первое означает «попросили то,
чего нельзя никому», второе — «попытались выйти за пределы выданного корня».

### Ограничения объёма

Предел размера файла, предел суммарного объёма на сессию, предел числа файлов в
одной операции. Рекурсивного удаления в релизе A нет вовсе: `file.delete`
работает по одному файлу, имеет семантику `at_most_once` и требует одобрения
везде, кроме временного рабочего корня.

## Публикация файлов

Схема — `security/schemas/share.v1.json`. Публикация — объект со сроком,
областью и обязательной аутентификацией, а не режим работы сервера.

Отправная точка конкретна: в исходной системе отдача по HTTP публикует домашний
каталог целиком и не требует пароля. Домашний каталог — это не «рабочие файлы»:
рядом лежат ключи SSH, профили браузера с сессионными cookie и хранилища
паролей. Поэтому:

| Правило | Как выражено |
|---|---|
| корень публикации — запись реестра с признаком `shareable`, домашний каталог им быть не может | реестр корней |
| аутентификация обязательна | `auth.required` имеет единственное значение `true` |
| пароля по умолчанию не существует | `auth.default_password` имеет единственное значение `false` |
| групповой адрес привязки невыразим | тип `bind_address` запрещает `0.0.0.0`, `::`, `*` |
| за пределами петлевого интерфейса — только TLS | правило `if/then` в схеме |
| срок обязателен, не более суток | `ttl_seconds` |
| перечисление содержимого выключено | `index_listing` |
| точки повторного разбора не разыменовываются | `follow_reparse_points` имеет единственное значение `false` |
| токен в заголовке, не в адресе | `auth.token_placement` |
| отдача вложением с запретом угадывания типа | `limits.content_disposition`, `limits.sniff_protection` |

Про последний пункт стоит пояснить. Если файл отдаётся с угадыванием типа и без
`Content-Disposition: attachment`, то загруженный кем-то HTML-файл исполняется в
источнике нашего узла и получает доступ к его данным. Публикация файлов
превращается в межсайтовый сценарий на собственном сервисе.

## FTP

Сервера FTP в контракте нет. Не «выключен по умолчанию», а отсутствует: в
перечислении `kind` схемы публикации значения `ftp` нет, и добавить его настройкой
нельзя.

Основания:

1. Учётные данные и содержимое передаются открытым текстом.
2. Прав на уровне объектов нет: доступ выдаётся на весь корень целиком.
3. Пассивный режим требует открытого диапазона портов, то есть отменяет
   осмысленное ограничение по портам на брандмауэре.
4. Встроенная реализация в исходной системе слушает все интерфейсы и имеет
   пароль по умолчанию. Это не ошибка конфигурации у нас, это состояние по
   умолчанию у них, и оно означает готовую точку входа в сеть с момента запуска.

Задачи, ради которых FTP включали, закрываются публикацией по HTTPS с токеном
(односторонняя отдача) и подкаталогом по SFTP (двусторонняя работа).

Отдельно: подключение **к** чужому серверу FTP как клиент — другая задача.
Устаревшее оборудование иногда не оставляет выбора. Такое подключение возможно
только через брокер, только по FTPS, только к цели из реестра и только по мешу.
Открытого FTP нет и здесь: перечисление протоколов в
`security/schemas/common.v1.json` его не содержит.

## Исходящий трафик

Схема — `security/schemas/egress-decision.v1.json`. Дополняет
[egress.md](egress.md), где описан рубеж на уровне узла; здесь — рубеж на уровне
вызова.

1. Разрешается группа назначений из реестра, а не имя хоста от вызывающего.
2. Решение закрепляет адреса, полученные при разрешении имени. Соединение
   устанавливается к одному из них; повторное разрешение имени перед
   подключением запрещено. Без этого имя, ведущее наружу в момент проверки,
   указывает на петлевой адрес в момент соединения.
3. Петлевые, локально-канальные, частные адреса, сеть меша и служебный адрес
   метаданных облака запрещены. Обращение к цели в меше идёт не через этот
   механизм, а через брокер с проверкой прав на машину.
4. Обращение к внешней модели — тоже исходящий трафик. Это записано отдельным
   значением `origin: ai_client`, потому что содержимое сессий, уходящее в чужой
   сервис, является утечкой независимо от того, как называется получатель.
5. Браузерный работник прямого выхода не имеет: только через фильтрующий прокси.

## Браузерный работник

Появляется в релизе B; контракт фиксируется сейчас, чтобы его добавление не
потребовало пересмотра границы.

**Отдельный субъект ОС.** Учётная запись `svc_af_browser`, свой профиль браузера,
никакого доступа к настоящему профилю сотрудника, к хранилищу учётных данных и к
защищённым областям.

**Содержимое страниц — данные, а не указания.** Работник возвращает наблюдения с
меткой `provenance: web`. Любой вызов инструмента, на аргументы которого повлияли
такие данные, помечается `derived_from_untrusted` и требует свежего одобрения
человека — это выражено правилом в `security/schemas/tool-request.v1.json`.

**Загрузки в карантин.** Отдельный корень, отметка о происхождении из сети
(`Zone.Identifier`), запрет выполнения, отдельное полномочие на вынос файла из
карантина.

**Сеть.** Только через прокси, с теми же решениями по исходящему трафику. Прямой
доступ к петлевым адресам запрещён: иначе страница, открытая работником,
дотягивается до сервера MCP на той же машине. Это второй рубеж к проверкам
заголовков из [agent-mcp-transport.md](agent-mcp-transport.md); ни один из них не
считается достаточным сам по себе.

**Учётные данные.** Вход в веб-приложение выполняет брокер, а не агент,
печатающий пароль в поле ввода. Пароль, введённый через автоматизацию
интерфейса, оказывается в дереве доступности, в журналах ввода и в контексте
модели.

## Что проверяется в приёмке

1. Относительный путь с `..`, с UNC, с `\\?\`, с двоеточием, с завершающей точкой
   — отвергается схемой.
2. Точка соединения, созданная внутри разрешённого корня и ведущая наружу, —
   отказ `containment_violation`.
3. Подмена компонента пути на точку соединения между проверкой и открытием — не
   меняет результата: работа идёт по дескриптору.
4. Запрос файла в защищённой области — отказ `protected_path`.
5. Публикация с адресом `0.0.0.0` — отвергается схемой.
6. Публикация без аутентификации или с паролем по умолчанию — отвергается
   схемой.
7. Публикация без TLS вне петлевого интерфейса — отвергается схемой.
8. Попытка создать публикацию вида `ftp` — отвергается схемой.
9. Исходящее соединение к `169.254.169.254` от браузерного работника — отказ
   `egress_blocked` с указанием диапазона.
10. Разрешение исходящего соединения без закрепления адресов — отвергается
    схемой.

# Контроль исходящего трафика

## Зачем

Главный риск чужого кода в нашем контуре — не то, что он что-то сломает, а то,
что он что-то отправит наружу: телеметрию, содержимое сессий, учётные данные.
Вырезать вызовы в исходниках недостаточно, потому что при следующем обновлении
они могут вернуться, а транзитивные зависимости мы читаем не построчно. Поэтому
нужен внешний по отношению к приложению рубеж.

## Что сделано сейчас

`infra/vps/setup-server.sh` ставит `ufw` в режим `default deny outgoing` и
открывает только необходимое: DNS, NTP, 80 и 443 для apt и реестра образов,
7844 для Cloudflare Tunnel, 51820 для WireGuard.

Честная оценка этого рубежа: он ограничивает **порты**, а не адреса. Компонент
уже не сможет открыть канал на произвольном порту, но обращение к произвольному
хосту по 443 пройдёт. То есть скрытая передача данных через HTTPS этим уровнем
не блокируется.

## Что нужно для полноценного контроля

Фильтрующий прокси с разрешённым списком доменов, через который обязаны идти все
исходящие HTTPS-соединения контейнеров, при полном запрете прямого выхода из сети
docker. Практически это выглядит так:

- отдельная сеть docker без маршрута по умолчанию;
- `HTTP_PROXY`/`HTTPS_PROXY` в окружении контейнеров;
- прокси со списком разрешённых имён: реестр образов, зона Cloudflare, зеркала
  пакетов;
- журнал отклонённых запросов как источник данных о том, куда приложение
  пыталось обратиться. Это же даёт проверяемый ответ на вопрос «звонит ли оно
  домой», вместо доверия к нашему чтению кода.

## Когда включать

После того как приложение заработает в штатном режиме: сначала собираем журнал
реальных обращений, затем превращаем его в список разрешённых. Обратный порядок
приводит к длительной отладке непонятных сбоев.
